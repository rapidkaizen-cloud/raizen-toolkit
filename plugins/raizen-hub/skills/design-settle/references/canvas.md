# The design canvas — taste decided on a free page, not by questions

One temporary TSX route — **every page of the app, redesigned** — where the visual direction and every shell are designed whole, judged in the real browser, then ratified value by value into Section 5. It replaces the long tail of taste questions a long-form interview would ask — everything beyond the reference question, the stack, and the direction frames; it never replaces those.

## When this path runs

- on every repo, after the reference slot of `interview.md`, the stack it recommends, and the install. The direction frames below are its first round.
- where UI exists, the same flow with *keep* first on every decision and today's look standing among the frames.

**Escalation when the canvas misses twice:** the interview re-opens — the reference slot again, with products chosen against what was rejected, then **a fresh set of direction frames** anchored to the new ticks — and the canvas is regenerated fresh from the new pick. The stack is not re-opened: it is installed, and nothing the two rejections said was about a package. The frames are redrawn rather than reused: the two rejections are the sharpest material this session has about what the user does not want, and a set that predates them has not heard it.

**`impeccable` and `frontend-design` are re-read before those options are written.** This is the only point in the flow where options are written twice, and the second time is the furthest the session ever gets from the material: two canvas rounds, a full product draft and a judgement now sit between the first read and this one. Options called *sharpened* but written from a decayed memory of the material are the first set again under a new name — which is precisely the failure that opened this escalation. The re-read costs one read and is the cheapest part of the whole escalation.

## The brief — features in, interpretation free

The input to the canvas is the **user's feature list**, plus what the PRD already holds. The user names what the app does; the canvas decides how that looks — composition, richness, hierarchy are the designer's to interpret, and the user judges the result rather than pre-approving a layout.

Two bounds on that freedom, both the user's own condition:

- **Function is faithful.** A feature on the canvas shows what the feature actually does — its real fields, its real states, the figures a business rule demands. What stays forbidden is the **untagged** invention: an improvised feature drawn without its proposal tag, or promoted without ratification. Tagged improvisation is not the exception this rule guards against — it is the canvas's job, granted below.
- **It renders working — static data, live chrome.** Real fixtures, not lorem; states, not placeholders. The **data** is static by design: nothing fetches, nothing writes, no auth, no validation, no business logic — real behavior arrives when pages are built through `build-flow`, whose Bound list is where *matches the function* is enforced page by page. The **chrome** is alive: sidebar and menu items navigate between canvas pages (plain anchors to the sibling files — no router import, the quarantine holds), tabs switch, a row opens its panel, dialogs and drawers open and close, the collapse collapses — local state over fixtures, nothing more. **An action whose real outcome is navigation navigates too:** the login button lands on the home canvas with nothing checked and any input accepted, a work-queue line lands on the page it points at — the walk from login to the deepest page works end to end, and no auth, no session, and no validation is simulated to make it so. The user judges flow as well as composition, and a canvas that cannot be walked is judged as posters; every interaction written here is real component code that survives promotion. A conditional branch that interaction cannot reach cheaply still gets its own frame, as Coverage requires.

**Assume the product whole — expansion is a duty, not a permission.** Before drawing, draft the full product this brief implies: from PRD Sections 1–4 and the designer's own knowledge of the domain — what a mature version of this app would hold, page by page. The product-type research `build-flow` Section 4 draws from is the floor of that draft, never its ceiling. The user naming two features is an opening, not the ceiling — **a canvas that renders a thin brief as thin pages has failed its job.** Draw the full draft, and **mark every improvised feature visibly as a proposal** on the canvas (a small tag on its section). The cut is then **asked, not narrated**: in the same AskUserQuestion call as the judgement verdict, the marked features form a multi-select — every feature an option with a one-line description, keeping all as the recommendation; four options is the tool's cap per question, so more features means more questions in the same call. What is unchecked is removed. Same bias `build-flow` applies per page — propose the full thing, let the user trim — but here the proposal arrives rendered, because a feature is easier to judge on screen than as a line in a list.

A kept proposal the PRD does not yet hold is reported as a PRD line for the user's decision, per `prd-format`: the canvas may show it, only the PRD makes it real.

**Where UI exists the floor of the brief is the app's function inventory, never its pages.** The audit reduces the existing pages to a written inventory — every function the app carries, one line each, page-agnostic — and that list joins the brief as given. What a page currently *holds* is not in the inventory: "session identity as a card on home" is an allocation the old design made, and the new direction re-allocates freely — a function may move to another page, into the chrome, merge with a neighbour, or shrink to a line. A function the new shell's chrome already carries is not drawn again as page content out of loyalty to where it used to live. Only a function absent from **every** canvas page is a cut, and a cut is asked at the judgement, never silent. Improvised features and reshaped shells are still expected and still tagged — a canvas that redraws today's pages in new tokens is a repaint, and a repaint has failed the job. *Function-faithful* binds what a shown feature does; it never binds a layout to what the layout used to be, nor a function to the page that used to hold it.

**In a redesign of an existing app, the current design is not an input — and Section 5's prose is the current design.** What the app *does* joins the brief as given; how it *looks* today does not — the canvas is drawn as if the app had no visual past, from the answers and the license below alone. That blindness covers the document, not only the code: the old Section 5's visual-direction prose, its signature, its ornament rules, and its archetype shell column are today's design written down, and the canvas may not read them as constraints. A signature worth keeping is re-drawn because the new direction earns it — tagged like any improvisation — never because a ratified sentence demands it. The audit's numbers exist to price the pass and to power the before/after at the judgement, never to anchor the new direction. **And the blindness is enforced by distance, not willpower:** the old page files are opened once, at the audit, to write the function inventory — the drawing phase works from that inventory and the answers, and does not reopen them; the Step 1 screenshots serve the judgement's before/after and the Step 8 comparison, and are not looked at while drawing. A rule that says "don't treat it as input" while the input sits freshly read in context is a rule that loses.

A reference the user points at — ticked or named under Other at the interview's reference slot, where it becomes one frame's anchor, or arriving later as a file, a screenshot, or a URL — is welcome as inspiration for the interpretation, and the picked frame's anchor, with anything named later, is what this canvas is measured against at the judgement (Judging, below).

**Measured, never transplanted.** What stays forbidden is moving its machinery across: importing its code, copying its components, reproducing its visual identity — a reference sets the direction, never the reproduction, and imitating a company's distinctive UI is refused however the request is worded. What is expected is the opposite failure's cure: where the reference is reachable — a screenshot the user attached, a public page the session can open — **look at it and take the numbers off it**, so density, type character, colour temperature and motion budget come from observation rather than from a memory of the app. Unreachable → say so, and say the direction is being drawn from memory; that sentence is what tells the user how much weight the anchor can carry.

## Asked before drawing

The reference slot of `interview.md`, alone; then the stack, **recommended rather than asked** — the library line with *own components* always among its alternatives, the icon line where the library bundles none, the engine dialogs a trigger fired — settled by the install block's approval, any line swapped by a reply in chat; then the direction frames and their pick, below. Nothing about the look is asked after the pick: what the picked frame carries is the canvas's baseline, and everything it does not carry is the canvas's own. Where UI exists the library line recommends keeping the installed library unless the audit indicts it, and every value later read from the picked frame is reported naming the value it replaces.

Install per the skill's own install step **before** the canvas is written. The canvas is built from the real packages, so they must exist.

**Assumptions are declared before drawing, in one block — mandatory, never skipped.** Every product and behavior call the canvas makes that no answer settles — layout calls, invented sections, data assumptions, conditional behaviors, the theme mode — is listed one line each (`GPS tolerance shown as a badge with live distance` · `bottom bar: 3 slots, input as the primary action` · `theme: dark by default, light offered — night shifts per Section 2`) before the first file after the pick is written — the frames precede it, carrying only their motivation and trade-off lines. **Visual values are not assumption lines** — palette, type, spacing, radius live on the canvas and are read at ratification; listing them here would report the same decision twice. Theme mode is the exception: light, dark, both, or following the system is a product call read from PRD Section 2 (`interview.md`), not a value read off the canvas. The block follows the derived-decision pattern: a report the user may cancel line by line, not a gate that waits. The same lines return at the judgement call, attached to what they produced, where the user settles them through AskUserQuestion like every other canvas decision.

## Directions first — the default, not the exception

**The frames run in every session, without exception.** They are drawn once the reference slot is answered and the stack is installed — the canvas's first round — and **nothing about the look is asked after them**: the picked frame is the direction, and its density, type, palette, surface, motion, and shell are read at ratification like every other canvas value. *Dense data-first* against *Warm editorial* as two lines of text is not a choice a junior developer can make; the same two on screen is the sharpest judgement they make all session, and a question that re-asks what they just chose on screen is answered by momentum.

Draw **2–4 direction frames**: each one drawn on **the proving page** — the page this app's direction is most visible on and most likely to break on, chosen by the designer per app and named with its reason in the frames' motivation lines, never fixed here. On a tool somebody reads every day that is usually its densest working screen; on a first-visit page, the hero with the section beneath it; on a field or phone app, the primary task screen. **One screen, or two where one cannot carry the direction** — a list with its detail, a hero with its first section — never the whole app, and never a set of posters. The proving page named here is held through the flow: it is what promotion moves first and the bar `build-flow` judges later pages against. The frames are drawn in the derived theme mode, named in the line that hands them over (`interview.md`). **How many frames, and what each one is anchored to, the reference slot's ticks decide** (`interview.md`): one frame per ticked product, `Decide for me` filling the rest to an anchor of the designer's choosing, a lone tick read twice on a named axis so the set is never one frame — and every frame names its anchor in its motivation line.

**They are drawn at full fidelity.** Type, colour, spacing, real copy, real fixture values. The details are the decision: everything that makes an interface read as generated lives in exactly that layer, so a grey-box sketch hides the only thing the user is being asked about. A wireframe can answer whether the boxes sit in the right places; it cannot answer whether a direction is bland, and bland is what this step exists to catch before a whole canvas is built on it. **Type included:** each frame picks its own faces and loads them by link — no install is needed to put a webfont in a canvas file — and the picked frame's pairing is the app's typography from that moment; nothing the user already approved on screen is re-argued as a name in a list, and the face's own package, where it needs one, is installed at ratification.

**They are drawn in the canvas's own format, in place, with the installed stack, on every path** — files under `src/design-canvas/` like every later round (TSX on the web; the platform's own page format off it, per *The canvas file* below), each named as the real page it draws with its candidate appended (`dashboard.warm-editorial.tsx`), every control drawn with the chosen library's component — or the canvas's own where *own components* was chosen — viewed on the running route and screenshotted at both widths under *Judging*. No second format and no later swap exists anywhere in the flow: the frame the user picks is already a canvas file, and a canvas file is already the production file, so nothing is transcribed, rebuilt, or exchanged on the way — what the user picked is what is promoted.

Four rules make the set a real choice rather than a rigged one:

- **Each candidate explores an axis that can be named** — *Warm editorial* against *Dense data-first*, not variant A against variant B. Five shades of one aesthetic is no choice at all, and a set whose candidates cannot be told apart in a sentence has not explored anything.
- **Each candidate carries an honest motivation and its main trade-off**, one line each. A set where only the favourite gets a case made for it is a rigged vote, and the user reads the rigging.
- **Names are stable.** Once a candidate is *Warm editorial* it keeps that name for the rest of the session — never renumbered, never renamed, including across a regeneration.
- **One is marked as the recommendation**, with a reason from this app.

**The design plan runs after the pick, never before.** The frames carry their own axes — rule two above already makes each one state its motivation and trade-off in a line — and that is the whole of what is announced beforehand: no palette, no pairing, no signature. A plan published before the candidates are drawn has decided the vote it is about to hold, which is the rigged set that rule forbids, and a plan written before the pick is a plan guessing at density and type.

The choice is one AskUserQuestion, single-select — the reference slot added ticks up into a set, the pick chooses one direction out of it — the frames on screen when it is asked: the running route, each frame's two-width screenshots, and **one side-by-side capture** from the entry route's compare page — every frame file rendered beside the others at the desktop width, an iframe each, the Keep candidate at its real route, nothing redrawn — handed over before the question is put, because a set judged one image at a time is compared from memory. An Other answer may carry a pick and a correction together (*the second one, but with the brand green*), or a mix (*the layout of the first with the palette of the third*) — read it as that frame with the change attached. **And the question text says how to reject the set**: *none of them — type what is wrong under Other and I draw another set*. Four frames already fill the tool's option cap, so that answer lives under Other; it redraws one fresh set to what was said wrong, under the same tick rules, the first set deleted — and a second rejected set opens the escalation above, two rejected sets being the same signal as two rejected canvases. What the user picks becomes the direction; the full canvas is then built to it under the rest of this file. **This costs one round and it is not one of the two correction rounds** — nothing was rejected, a decision was taken.

**One refine round, only when the pick carries a change.** A clean pick goes straight to the design plan. A pick carrying a correction or a mix is redrawn once as the picked frame with the change applied, **plus one screen of a second archetype** — the one the direction is most likely to break on next (a form or a detail beside a table; a section beneath a hero; a detail beside a list) — shown at both widths and confirmed with one AskUserQuestion: use this · adjust it once more · back to the set. It is not a correction round and is not counted: the first screen is the change the user asked for, seen before a whole canvas is built on it rather than discovered after; the second is the cheapest proof that the direction survives beyond the page it was picked on. *Adjust it once more* runs once; after it the design plan follows whatever stands. **The unchosen frames survive until this round closes**, because a mix reads from them; then they and the compare page are deleted rather than kept as alternatives.

**The chosen frame is carried into the canvas, never redrawn from nothing.** It is a full-fidelity screen of a real page of this app and already a file in `src/design-canvas/`, so it becomes that page's first canvas round in place: renamed to the name its real page carries, then finished to the rest of this file — every state drawn, fixtures moved into the one contract-shaped file, the three self-check scans run. Redrawing a screen the user has already approved on screen throws away the one artefact this whole step exists to produce, and risks arriving at a page they liked less than the one they picked. What changes on the way in is addition only — the remaining states, the fixtures moved, the other pages drawn around it — and the correction the user attached to the pick, applied where the frame departed from it. A departure large enough that the page no longer reads as the frame the user picked is a line at the judgement, not a silent redraw.

**Nothing stands the frames down.** A reference the user ticked is a direction, and the frame drawn to it is that direction on screen — a second reading of it, or the designer's candidates beside it, is what lets the user confirm the words meant what they thought before a whole canvas is built on them. A brand palette to follow is a constraint every frame is drawn under — colour derived from it per `impeccable`'s colour derivation — not a substitute for the set. Where UI exists, today's look, where Keep was ticked, is one of the frames — the running app at its real routes, never redrawn. Every session draws, including one where the user seems to know what they want: knowing it in words is what the frames are cheap insurance against, and a wrong guess here costs a correction round that redraws the whole app rather than three screens. The canvas built from the pick is then measured against the picked frame's anchor at the judgement (Judging, below).

## The canvas file

**One folder, one file per page.** `src/design-canvas/` beside the styleguide route: one TSX file per page (on a non-web platform, the platform's own page format and source layout — the folder-as-quarantine, one-file-per-page, and naming rules hold unchanged), **named exactly as its real page is or will be named**, plus an entry route that lands on the primary role's landing page (the chrome's nav is the page list) and one CSS file carrying the canvas variables. Reachable dev-only like `/styleguide`, out of navigation and out of the production build. Never one monolithic file, and never files scattered outside the folder — the folder is the quarantine boundary, and its structure mirrors the app's real pages **so that approval is a promotion, not a rebuild**. **A file more than one page imports — a shared wizard, a shared card — is not exempt: it names its production path in its own header line, decided at the round it is created, and enters the pass's file plan as its own line.** Without that path there is no file to copy it to and no pair to diff, so the composition the user approved is re-assembled by hand from its parts, and every page built on it is a repaint.

**The canvas is the final front-end, staged.** Its files are not illustrations of the future pages — they are the pages, held in a separate folder only because the user has the right to reject them before they replace anything. That is why every file is written production-grade from the first round: real library components, production token names, and **every state drawn** — the loading skeleton, the empty state with its wording, the failed state, the busy state — because a state added later, during promotion, is markup the user never approved. **Fixtures live in one file, shaped as the data contract** the real layer returns — `build-flow`'s contract shape where no data layer exists yet, the existing modules where one does, enforced by the scan below. Promotion then swaps one import and the markup body never changes: the only legitimate source of difference between a canvas file and its live page is the data flowing through it.

**Every page, drawn.** Derive the archetype table before drawing — group the PRD's pages as `interview.md`'s archetype rule describes; where UI exists, the **grouping** comes from the routes that exist, and that is all the old app contributes. **Each archetype's shell is proposed fresh, from the new direction** — the picked frame's shell, the brief, and the designer's own judgement of what this kind of screen needs; the shell a page has today is never the template, and it surfaces only as the *old* column of the judgement's shell question. A derivation that reads the existing page to learn "what this archetype's shell is" has imported the old design through the one door left open for routes. Then draw **every page**, each to its archetype's proposed shell — content from the function inventory where UI exists, from the PRD where it does not. Pages sharing an archetype will read similar; that is the app being consistent, not the canvas being lazy. This is the full redesign, visible up front — the whole app before a single real file moves.

**`/styleguide` is generated before the canvas** — before its first round, the frames — to Step 6's spec, rendering the current theme — library defaults on a fresh app. It imports production tokens, so when ratification later writes the new values it follows by itself. Nothing on the canvas depends on it, but the component inventory existing first keeps the canvas honest about what the library actually ships. **Where UI exists the route may already exist and keep rendering the old theme — leave it alone until ratification, and the canvas never looks at it**; regenerating it first would put the old design on screen in the very session that must draw without it. An older app with no `/styleguide` at all waits the same way: the route is generated inside the pass, from the new tokens, as Step 7 orders it.

**Quarantine, both directions.** Nothing in the app imports the canvas, and the canvas imports only from the **declared UI stack** — the chosen component library, the chosen icon pack, the engine libraries the app's dependency file carries for UI jobs (charts, table engines, date pickers, drag-and-drop), and its own CSS. Never the production theme, tokens, or components — the canvas is pre-ratification, and its values are its own until the user ratifies them. The line between the two: a library in `node_modules` is neutral machinery; a production component carries the old design. The app must render identically with the canvas deleted.

**Real components, canvas-owned theme.** The library's components render inside a scoped theme wrapper carrying the canvas's own values — CSS variables on the web. What the user judges is what the app can actually become — no hand-drawn mockups whose fidelity dies in transplant, and no production theme touched while the canvas iterates. **Element selectors in the canvas CSS style native controls only, never the elements inside library components** — a round that swaps native controls for the library's leaves old `input`/`select` rules behind, and they double the library's own borders; scope them out (`:not([data-slot])` or equivalent) the moment the swap happens. **And every control the chosen library ships is drawn with the library's component** — button, input, select, tabs, chip, dialog, pagination, all of them, from the first round, not as a correction the user has to ask for. Hand-rolled markup is legitimate only where the library has no component for the job (a virtualized data table, a bespoke signature element), and each hand-rolled control is named as its own line in the judgement call. **Answered *own components*, every control is the canvas's own and none of them is a line** — the set they form is the app's component set, bound by `ui-build`'s reuse rule from its first extraction, and a second form of one control across pages is the finding, not the hand-rolling. A canvas that re-implements the library's buttons has not shown the user what the app can actually become.

**The declared stack binds the engines too.** A job an installed engine owns — a chart, a virtualized table, a date picker — is drawn with that engine, never re-implemented beside it: the promoted page must be the canvas file, so an engine the canvas avoided is an engine the app loses without anyone deciding it. Hand-rolling where an engine covers the job is a departure line at the judgement (`recharts installed → drawn as CSS bars, because Z`), and swapping or dropping an engine is an explicit decision the user answers there — never a side effect of approving pixels; an approved swap becomes its own install/remove line in the pass. Everything the canvas draws with is installed **before** drawing, per the skill's install step. **And before each round is shown, the canvas self-checks itself** — three scans, and a round that fails any of them is not ready to show:

1. **Imports.** Every control maps to a library component or stands as a named hand-rolled line — with *own components*, to the canvas's own shared set — and every engine import comes from the declared stack.
2. **The render.** Run `impeccable`'s detector over the round's files first — it is deterministic and it owns exactly this scan's subject: clipped and overflowing containers, occluded and overflowing text, broken images, script errors. Fix what it reports here; those are defects, not direction, and deferring a defect to Step 8 ships a broken round to the judgement. **Only the defect class is acted on in a round** — a hit that is a judgement about the direction (nested containers, uniform spacing, a colour family) may be the very thing the user is about to choose, so it travels to Step 8 with the rest. Detector absent, or a rule it cannot see: take the round's screenshots **first and read them yourself**, before the user does. A frame whose content overflows or clips its container, a label naming a size the frame does not actually show, a state drawn as an animation that a still frame renders as nothing — all of it is fixed now. The screenshots are already mandatory (Judging, below), so this scan costs the reading, not the capture. Its licence is narrow on purpose: **clipping, overflow, and labels that lie**. It is not an invitation to re-open composition the moment before showing it.
3. **The arithmetic.** Every number printed as a claim — a ratio, a percentage, a count, a total — is computed, never recalled, and the fixtures close (Coverage, below).

The scan is reported with the round as a short list of what it caught and fixed, not as a claim that it ran. **Where UI exists the scan covers the fixtures too**: value types and field names come from the existing contract or data-layer modules — an enum, a state label, a column name — and no type name already used there is redefined with different values. Page-structure types are not imported: filter shapes, page sizes, and query keys stay the canvas's to redesign. A field with no source in either is drawn tagged as a proposal, so the user decides it at the judgement rather than meeting it as a dropped element after the pass. An engine need that only emerges while drawing follows `engine-rubric.md`: the frame is drawn with the no-engine rendering and tagged, the judgement settles it, and an approved adoption installs the engine and redraws that frame in the next round.

**The taste license, granted explicitly.** Design the page as a designer with a free hand — no obligation to any earlier conservatism. Everything the picked frame did not settle the licence owns outright: palette steps, tinted surfaces, elevation, type scale, spacing, the composition of every other page. What the user did settle — the picked frame, the correction attached to it, a reference they named — is their **preference — the baseline, not a cage**: the license still covers everything, and **departing is part of the job, not an exception to argue for**. Where the designer judges a better call than what was picked, draw the better call, tag it, and ask — one line per departure in the judgement call, shaped `picked X → drawn Y, because Z`. The user settles every departure there: an unapproved departure reverts to what was picked; an approved one enters ratification like any other canvas value. What the tag protects is the user's authorship, never the pick's immunity — a canvas that obeys every pick it privately judged wrong has withheld its one useful opinion.

**The licence covers `frontend-design`; `impeccable` is the floor it stands on.** `frontend-design` is a default the direction is chosen against, not a second client: the designer may depart from any value in it — a palette count, a family count, a composition habit — the same way as from the pick: drawn, tagged, its reason on one line, settled by the user at the judgement. Never silently. `impeccable` is different in kind: it is the corrector, the one thing in the flow that keeps the result from reading as generated, and its Refuse list, its Verify list, its calibrations, and its detector bind every round as they are written. A Refuse-list item is never a departure the designer grants itself: it is fixed, or it stands at the judgement as a finding under the detector's own name for the user to settle; a face on the calibration list is chosen only with its reason written in the design plan. And what no direction departs from at all are the floors `interview.md` lists as rules rather than preferences — contrast, colour never the only marker, reduced motion honoured, a visible label for every field, the platform's touch targets — and the engineering rules of this file: the quarantine, the token names, the fixtures that close, the one-to-one promotion.

**And the licence carries a duty: one signature.** Every canvas draws a **single element this app is remembered by** — a treatment, a shell move, a way one recurring thing is rendered — and it is where the boldness is spent. Everything around it stays quiet and disciplined; a canvas where three elements compete to be the signature has none, and a canvas with no signature at all has produced a competent average, which is the outcome this whole path exists to avoid. The signature is **tagged on the canvas like a proposal** and settled by the user at the judgement as its own line, because it is the one decision most likely to be the reason a direction is accepted or rejected. `frontend-design` holds the method the direction it serves is chosen by.

**Loaded once, in hand throughout — never re-read step by step.** The material arrives before the reference slot and stays for the design plan, every canvas round, the judgement, and the ratification; the only second read in the whole flow is the escalation above. A step that reloads it pays the context twice for the same rules.

**Two pieces of material are loaded before the reference slot, not at drawing time: the Required installs `impeccable` and `frontend-design`.** The reference options and the frames are the first place taste is exercised, so a set drawn before the material is read offers the user a menu of the very defaults the material exists to close — and a choice never offered is not recovered by any later round. By the time the canvas is drawn they have been in hand since the interview. Both are divergence guidance — they name the templated defaults to avoid and the method for choosing a direction, without naming the direction. Material, never an authority: where any of them collides with a user answer or a ratified value, the user wins. One absent, the other still loads, the absence is asked under Step 1's rule, and the round says which one was missing.

**What crosses the genre line from `impeccable`, and what does not — named by role, located through its own index.** It ships far more than material, so the boundary is drawn by what a piece does; where each piece lives is read from `impeccable`'s own `SKILL.md` at load time, never from a file name remembered from this text, which goes stale the moment its layout changes. **Crosses:** its **craft floor** — the Refuse list, and its Verify list as a build-time check rather than an interview input; its **two calibrations for new work** — the training-data display faces that mean the model stopped looking, and the clusters AI interfaces converge on; and its **operational register** entire **on an operational app** — type families, scale, motion budget, overlays, as it states them; a landing page does not load it, its register is the wrong one there. **The Refuse list crosses by what it forbids, not by the CSS it names** — a ban written as a selector is read as the visual result it prevents, so it holds on a Surface whose code carries no selectors at all. **Does not cross:** its own **direction pipeline** — its interview, its dice roll over directions, its decision server, comps, and its **agents** (at the time of writing a finish reviewer, a documenter, an asset producer, and a manual-edit applier), none of which this flow spawns. Adopting those replaces this flow rather than informing it, and `PRD.md` stays the only decision document. **No `impeccable` command that writes `PRODUCT.md` or `DESIGN.md` from the built world is run in these repos** — `init`, `document`, `extract` at the time of writing — because those decisions live in PRD Section 5, and a `DESIGN.md` written from shipped code is the `CSS → PRD` direction this skill's hard limits forbid. The `/impeccable` menu leads with `init` whenever it finds no `PRODUCT.md`; that offer is answered by pointing at Section 5, not by taking it. **The one `DESIGN.md` that exists is the one Step 6 generates from ratified Section 5 values** — direction `PRD → file`, frontmatter only, regenerated by this skill alone, never hand-edited — because the detector's design-system rules read their system from that file and from nothing else; without it, drift from the ratified system is invisible to the hook in every later session. A role `impeccable` no longer carries is reported at the Design material row, never invented. **The detector reads HTML and CSS, and that decides where it runs.** A web UI qualifies, and so does a desktop or mobile shell whose UI is web technology — Tauri, Electron, Capacitor — because the files it scans are the same. A **truly native** surface does not: SwiftUI, Compose, XAML and their kin compile from source the rule engine has no verdict on, and Impeccable says so itself. Where PRD Section 1's Surface names one of those, every detector instruction in `design-settle` is skipped and reported as `n/a — native surface`, never run and never counted; the checks those steps still owe come from the Surface's own Proof profile. Reporting a zero from a scan that could not read the code is worse than reporting nothing.

**A native Surface loses the detector and gains its platform references in its place.** `impeccable` ships a reference for iOS and one for Android — safe area and window insets, the platform's own navigation metaphors, the platform type scales, and the touch-target floors as each platform states them. They are loaded alongside the craft floor wherever Section 1's Surface names that platform, both of them on an adaptive one, and they carry the rules a web-shaped floor states differently or not at all. Web technology loads neither. **A desktop Surface — shell or native — has no reference yet.** `impeccable` ships none for macOS or Windows, and this skill carries none until the first desktop app ships and `references/macos.md` or `references/windows.md` is written from it. Until then the target OS's design language is drawn from model knowledge, said so at the Design material row, and the side-by-side proof under Judging is the only floor holding the app to its platform.

**And two of its playbooks route by platform the way this rule does, so they are named by role rather than left to be discovered:** its **audit** playbook, web and native, covers the technical dimensions Step 8 verifies — accessibility, performance, theming, responsiveness, implementation integrity — with the touch-target floors this repo no longer states anywhere else; its **adapt** playbook, web and native, carries the width and device-class rules. Read the one matching Section 1's Surface when a step needs a floor or a device-class list; the rest of them are command playbooks and stay outside this line.

**And one collision, decided here:** its colour-derivation reference builds OKLCH ramps by varying lightness and reducing chroma at the extremes. Where a ratified Section 5 line says otherwise, Section 5 wins, as it does over every line in this file.

**What crosses the genre line from `frontend-design` depends on the Register switch — judged on the first visit, or on the tenth use — derived at `app-settle` question 1 and re-derived from PRD Section 2 whenever it is read.** It is written for the open web, and its body leans toward marketing pages — the hero as a thesis, landing-page anatomy, the question *what makes this unforgettable*. **Where the register is the tenth use** — a tool somebody comes back to — read it for what transfers and leave the rest: **the calibration** (the defaults that read as generated), **the two-pass method** (state the plan, critique it against the brief, say what changed), **the signature**, and **the restraint** — spend the boldness once, then remove one thing. What does not transfer there is the marketing anatomy, and chasing *unforgettable* with anything that costs speed of use: **the aesthetic risk is the signature and nothing else** — one element, not a posture worn across every screen; a dashboard somebody reads forty times a day pays for a posture every one of those times. **Where the register is the first visit** — a landing page, a marketing site, any page whose job is to explain and convert — **the whole file crosses**: the page is judged on that visit, the hero is the thesis, the landing anatomy is the brief's floor, and a posture worn across the page is allowed — the signature is still drawn and still named as its own line at the judgement, so there is one decision to answer, and the calibration and the restraint still bind. **A product carrying both registers** — a public front and a logged-in inside — takes the first-visit branch on its front pages and the tenth-use branch behind the login, per page group. `impeccable`'s floor applies whole on every branch; this boundary is about the other file.

**The line the ban actually draws.** What is never loaded is a skill that names **the look** — a fixed palette, a fixed pairing, a card recipe, a shadow scale to copy — because read for every app, a house style makes every app look like the house. What is loaded, and must be, is guidance that **narrows the space the look is chosen from**: the defaults that read as generated, the formula that keeps two accents in one family, the four typefaces that are a failed choice rather than a safe one. The first names a point; the second removes a region. A canvas given the taste licence and no material at all is not neutral — it falls into the defaults, and *generic* is the name of that failure, not an accident of it.

**The canvas carries its own foundations board, as a page of its own** — palette roles and steps with their values, text scale on real sentences, spacing, radius, shadow, status triads — rendered from the canvas's own variables: a live preview of what `/styleguide` will hold permanently once the values are ratified. **The entry route lands on the primary role's landing page, never the board** — the canvas is judged as the app, and its first impression is a working screen, not documentation. The board hangs in the canvas chrome's nav as its own entry, **set apart from the page groups** so it cannot be mistaken for an app page — one click from every page wearing its values. **And it renders inside the same chrome shell as every other canvas page** — sidebar, top bar and content area where that is the shell those pages wear; only its content is the system rather than the app. A board rendered bare breaks the one navigation pattern the canvas exists to demonstrate.

**How a token is shown: applied to itself, every other variable held constant. Never a table row.** A list of nouns is satisfied by two columns of name and value, and two columns of name and value is the generic output this path exists to prevent. So:

- **Spacing** is a square literally that many pixels, the steps set side by side so the ramp is a staircase. A degenerate value still renders a labelled marker rather than nothing — floor the drawn size.
- **Radius** is identical tiles differing only in corner, so the eye compares corners and nothing else.
- **Shadow** is identical surface tiles that actually cast, with vertical room around them so the shadow falls instead of being clipped by its neighbour.
- **Border width** is identical tiles differing only in stroke.
- **Colour** is a swatch of fixed size carrying the step name, the resolved value, and the semantic alias that points at it — with a hairline inset ring so near-white steps keep an edge. **Grouping is carried by the gap**: tight inside one ramp, looser between families, so the structure is read before anything is labelled.
- **Type** gives every step **a different real sentence from this app's own domain** — the sentence that step actually carries on a screen. One repeated neutral string is allowed on the weight specimen alone, where holding the words constant is the point.
- **The alias layer gets its own row**: role, the step it points at, the resolved value. That layer is the API the components actually use, and a board that shows only numbered steps has documented the palette while hiding the system.

**Every specimen carries a caption in one identical treatment across the whole board** — monospace, muted, small — printing the token key **and** its resolved value together (`lg · 8px`, `hairline · 0.5px`). An absurd literal is relabelled rather than printed (`full`, not `9999px`). The caption is what makes the board usable by an engineer instead of only viewable by the user.

**And the board carries the contrast section** — one row per foreground/background pair the theme defines, in every ratified theme mode, the two colours rendered live as a chip of the real foreground on the real background, the computed ratio printed beside it, and its mark against the 4.5 / 3.0 floors. Ratification (below) is where the numbers come from.

**The canvas's variables carry the production token names.** The vars are the canvas's own, but named exactly as the theme files will name them — ratification is then a copy, not a translation, and nothing gets renamed on the way into production.

**Coverage.** The whole visual language, shown once across the pages: every color role in use on real surfaces · text steps on real sentences · the app's densest data view with messy fixtures (long labels, large numbers, missing values), where it has one · form controls in their states · **every conditional branch of a form as its own frame — a status that reshapes the fields (deal / no deal) is two frames, never one frame with a note** · status markers · one card or KPI group · **the busy state of every long-running operation — import, matching, bulk delete — as its own frame, carrying real counts** · the loading, empty, and failed state of every page that has one, drawn as frames — promotion adds data, never markup · the behavior at both widths. Realistic domain data from PRD Section 4 — the same standard `build-flow` holds every page to.

**And the numbers must close.** `contract.md` already prefers fixtures **copied** from the document the app replaces, and copied rows close by construction — this rule is for the case that file names as the fallback, where no real document could be used and the figures were invented. Invented figures are plausible one widget at a time and incoherent across a screen, which is exactly what makes a dashboard read as a mockup instead of a report. So on every page:

- A headline total equals the sum of the parts rendered beside it, and a remainder equals the difference it claims to be.
- A percentage, a ring, or a progress bar equals part over total to the precision it displays.
- A top-N list sums to less than its headline, so the tail it implies is plausible.
- A bar width is **computed from the value printed next to it**, normalised against the largest in the set — never a width typed by hand.
- A pagination label's range matches the rows actually rendered, and its last page equals the total divided by the page size, rounded up.
- A sort affordance's claimed direction matches the order of the data underneath it.
- One fictional record named in two places is named identically in both.
- Totals are **derived from the fixture array** rather than typed as literals, so the two cannot drift apart in a later round.

Numbers, dates, thousands separators, and currency follow the app's own locale, as `CLAUDE.md`'s Locale row states it.

**One pattern per recurring control.** Row actions, pagination, summary bars, filter rows: each takes exactly one form across every page — the active page visibly marked, the same action affordance on every table. A second form of the same control is a finding at the judgement, not variety. And **fixture text and labels are written in the user's language** — the canvas is the app being judged, and its strings follow the same language rule as production screens.

## Judging

**The platform is proven, not assumed — and the proof is a list, not an impression.** PRD Section 1 names the platform. On anything other than the web, put the canvas beside one real application native to that platform — the picked frame's anchor where it is native, otherwise one named at this step — and write the differences out one by one: window chrome, navigation shape, control size and radius, icon family, type, accent. Each difference is then either a **departure** with its reason on one line, or a **correction round**. "It looks native" is not an output; the list is, and a list nobody could have written means the comparison was never made.

Why it is a rule rather than taste: every other gate here measures the canvas against this app's own answers, so an app that answers every question in the web's vocabulary passes all of them and still arrives looking like a web page in a window. This is the only step that measures it against something outside itself. On the web that trigger does not fire — there is no OS language to diverge from.

**The same list runs, on any platform including the web, whenever the picked frame names an anchor** — a product the user ticked or named under Other, or one the designer chose under `Decide for me` and named in the frame's motivation line. An anchor is what the canvas designs toward, and an anchor nothing is measured against is a wish. So put the canvas beside it and write the differences out one by one — density, colour temperature, type character, motion budget, shell shape, how a recurring control is rendered — and settle each one as a **departure** with its reason on one line, or as a **correction round**. *"It feels like the reference"* is not an output; the list is, and a list nobody could have written means the comparison was never made. The anchor is what the list is written against, not what the canvas is made to imitate: the bound in "Measured, never transplanted" above still holds, and a difference kept deliberately is a departure like any other, not a failure.

Screenshot at the Section 5 desktop breakpoint (1440px when none exists yet) and at the derived lowest supported width, with the browser tooling available to the session. On a platform whose PRD Section 1 Proof profile names something other than a browser, capture through that profile's Visual line instead — same two bounds, or the platform's equivalent.

**Shown inside its device.** The narrow capture is presented inside a phone frame and the wide one inside a window frame — a bare browser screenshot reads as a web page rather than as a design, and the frame is what tells the user which of the two bounds they are looking at without a caption. **No fake chrome inside the frame**: no painted status bar, no painted keyboard, no fake tab strip carrying content — on a real device the real ones render on top of the layout, and a painted copy reads as doubled. **The frame belongs to the canvas chrome — the entry route — and never to a page file**, so promotion still copies the page element for element and the diff stays confined to the data seam. A session with no capture tooling reports the run target and both widths as it does today; it does not draw a frame around nothing.

The user judges. Two **correction** rounds on the same canvas — rounds opened by the user rejecting what was drawn; a third does not run, the canvas has spent its rounds, and the escalation above opens. A round opened by the user **asking for something new** is not one of those and is not counted; it quotes the request it serves, and a round that cannot quote one is a correction round. Without that split the cap is refused rather than obeyed — a session told to escalate over a request the user just made will write itself an exception instead, and an overridden rule costs context in every session while protecting nothing.

**Escalation decides values, not pixels.** Its answers become the brief's constraints, and the canvas is **regenerated fresh from them** — never patched over the failed one — then judged again under the same two-round rule. **Regeneration replaces the direction, never the decisions:** every feature proposal the user already approved and every shell already ratified carries into the regenerated canvas. A fresh canvas that arrives without an approved feature has silently reopened a settled decision — a page that was full last round and is empty this round is that failure showing.

**Every decision in this path goes through the AskUserQuestion tool**, under the rules `interview.md` states — a prose question at the end of a turn is answered by no one. **Every label in those dialogs is written in the words the user uses, never this file's** — *ratify*, *seam*, *archetype*, *departure* are vocabulary for the session, and a label the user has to decode is a dialog answered blind. Say the action instead: keep this value, use the new layout, delete this page. The judgement is one call: a single-select verdict (approve · rework this round · escalate to the questions), the marked-feature multi-select above, the answer-departure lines for answered slots, and the shell questions — where UI exists one per archetype, old shell beside new, **departed or not** (a shell question asked only on departure makes sameness free and departure costly, which is the anchor working); where it does not, one per archetype the user's archetype-table correction did not already settle. Four questions per call is the tool's cap — more archetypes means a second call in the same turn. Contrast failures, cancelled value lines, and reopened questions are asked the same way.

**The signature is its own question, asked on its own.** Not a line riding the verdict call among six others — one AskUserQuestion, naming the element, saying what it costs the pages around it, and offering keep · redraw it once · drop it and accept the quieter page. It is the single decision most likely to be the reason a direction is accepted or rejected, and the licence exists precisely to stop the canvas settling into a competent average; a question that arrives as item four of seven is answered by momentum, not by judgement. **A user who cannot recall being asked was not asked**, whatever the transcript shows. A signature the user rejects is redrawn once — never dropped silently, and dropping it is an answer only the user gives.

**Two more lines ride the verdict call whenever they exist**, each settled like a departure: the **reference differences**, against the picked frame's anchor · the **direction candidate** the user picked, named, so a later round cannot quietly drift off it.

## Ratification — approval happens on the canvas, the values follow as a report

**Approving the canvas is the approval.** The values behind it are then read — the canvas's variables and measured values: palette and its steps, type scale, spacing, radius, shadow, density numbers, and the picked frame's anchor, which Section 5's Visual Direction records as the reference the app was designed toward — and reported the way derived decisions are reported: one line each, never silent, cancellable. Cancelling a line reopens that value as a question; the rest proceed. There is no second approval gate over the same pixels the user just judged.

Two cases still stop:

- **Contrast — computed, never recalled.** Every foreground/background pair the theme defines, in every ratified theme mode, is run through the WCAG relative-luminance formula and the ratio is **calculated**: a ratio written from memory or judged by eye is the one error a handoff document must never carry, because everything downstream trusts the printed number instead of re-measuring. Compute it where the board renders — the foundations board already carries the contrast section (above) — so the numbers and the chips come from one source and cannot disagree. Every semantic family's dark shade is **chosen by measuring it against its own light shade until it clears 4.5**; that is what the dark shade is for, and picking it one step along the ramp is how a badge ends up unreadable. A failing pair is put to the user, never silently passed and never silently fixed. A passing pair still prints its number.
- **Where UI exists.** The app already holds today's values, and a filled Section 5 changes only by explicit user decision — so the report is not enough: the values enter the gate (Step 6) as the *new* column of the diff, and that line-by-line approval is the one gate. The canvas judgement and the diff never double up; the diff is where the old value is protected.

Ratified values are written into Section 5 and the styling files under Step 6's rules, all five — where UI exists, only after its gate approves, as the pass's first act on its own branch. The styleguide already exists and follows the new tokens by itself — verify it against Step 6's done-check, then the pass runs.

**No reference page exists — the canvas is the reference, and approval promotes it.** The canvas pages are structured like the real ones, so the pass **copies each file to its real path** — the proving page first — removes the canvas theme wrapper (the token names are already production's), and replaces the fixtures with the real data layer as `build-flow` and `logic-settle` prescribe. **Copied means the canvas file becomes the page** — a production page rebuilt by re-tokening its old markup is not promoted, however redesigned it reads under the new chrome. **And promotion is element-for-element**: every visible element of a canvas frame either survives into the page — fixtures swapped for data, real states added — or appears as a named deviation line at the recap with its reason (real behavior contradicts the drawing · the backend does not exist yet · the control is obsolete). Substituting a plainer equivalent silently — a bare file input where the canvas drew a dropzone — is a failed promotion; and the reverse case, a canvas control the real flow never had, is a canvas error to report for the user's decision, never to quietly drop. **The proof is a diff, not a look**: put the canvas file beside the promoted page — the differences must be confined to the data seam (the fixture import swapped for the data layer, plus its loading and error wiring) and to approved deviation lines; any other difference is a failed promotion to fix, whichever side reads better. **And the foundations move first**: everything the canvas CSS carries beyond token values — the font loading itself, element-level rules, shadows, motion durations — lands in the production styling files before any page moves, and is verified in the browser by computed style: the fonts must resolve to the loaded webfonts, not to a fallback stack. (The web profile's check — a platform whose Proof profile names no browser verifies the equivalent through its Visual line, and says what could not be verified.) A token grep cannot see a font that never loads. **The shared chrome components a canvas page imports are part of that promotion**: each one lives in the production chrome before any page importing it counts as moved — a shared wizard or card dropped on the way over silently downgrades every page built on it to a repaint. **The ratified original stays behind, frozen** — the lifecycle below says when it dies. Where no backend exists yet, promotion keeps the contract fixtures in `build-flow`'s shape, and real wiring arrives page by page through the queue; where a data layer exists it is wired in the pass itself. What is checked per page, at both widths, is **survival of real data**: a layout that collapses under real rows, a token that did not land, a section that vanished — that is divergence, and the first one stops the pass as a rework round of that page, two at most before Section 5 reopens. Real rows differing from fixtures is not divergence. `/styleguide` embeds no page — the app itself is the composition, one route away. The proving page simply remains the bar `build-flow` judges later pages against.

**A ratified canvas file outlives its promotion as a frozen reference, and dies with its page's real implementation — never before.** The user approved those pixels; until the real page carries real data and survives both widths, the canvas file is the only thing to compare it against. Three rules keep that from becoming drift:

- **Frozen.** A ratified canvas file is never edited again, and never a source of values or patterns — Section 5, the theme files, and the promoted page are the sources; the canvas file is comparison only.
- **Deleted per page, beside the proof — and only with the user's word.** The session that wires a page with real data and sees it survive both widths puts the real page beside its canvas file, fixes what silently diverged, then **proposes** the deletion at a chat stop — naming the page, inviting the side-by-side look, then ending the turn; never through an AskUserQuestion, which would cover the comparison being read — and deletes only on a granted confirmation. Never delete unasked: the canvas file is the only comparison the user has, and a session convinced of its own parity is exactly the session that must not be the judge of it. `build-flow` carries this for pages wired later through the queue; where the pass wires in-session, one confirmation at its verification step covers the whole canvas.
- **Remnants go last.** The entry route, the foundations board, and the canvas CSS are deleted when the last page file goes — the CSS's values have long lived in the theme files by then.

A canvas file that outlives its **implemented** page is the second source of values the styleguide exists to prevent — that, not the comparison period, is the failure.

## What the canvas never decides

Page content (`build-flow` Section 4) · the archetype table — the canvas proposes every shell on screen, but the table becomes real only through the user's archetype-table correction and the judgement's shell answers · loading, empty, and error norms (`ui-build`) · anything the user does not ratify.
