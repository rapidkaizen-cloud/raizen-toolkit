# The design canvas — taste decided on a free page, not by questions

One temporary TSX route — **every page of the app, redesigned** — where the visual direction and every shell are designed whole, judged in the real browser, then ratified value by value into `DESIGN.md`. It replaces every taste question beyond the interview's dialogs, the direction question, and the direction frames; it never replaces those.

## When this path runs

- On every repo, after the interview (`interview.md`) and the install gate (SKILL.md Step 4). The direction frames below are its first round.
- Where UI exists, the same flow with *keep* first on every decision and today's look among the frames.

**Escalation when the canvas misses twice** (or when two frame sets are rejected): re-read `impeccable` and `frontend-design` first — the only second read in the flow. Then run the reference search again, steered away from what was rejected, ask the direction question again from its results, draw **a fresh set of direction frames** to the new answer, and regenerate the canvas fresh from the new pick. Do not re-open the stack or the four product calls; a rejection that names a product call re-asks that one dialog alone. Never reuse the old frames — they predate the rejections.

## The brief — features in, interpretation free

The input is the **user's feature list** plus what the documents hold. The canvas decides how it looks; the user judges the result rather than pre-approving a layout. Two bounds:

- **Function is faithful.** A feature on the canvas shows what it actually does — its real fields, states, and the figures a business rule demands. Never draw an improvised feature without its proposal tag, and never promote one without ratification.
- **It renders working — static data, live chrome.** Real fixtures, not lorem. The **data** is static: nothing fetches, writes, authenticates, validates, or runs business logic. The **chrome** is alive, as local state: nav items navigate between canvas pages (plain anchors to sibling files, no router import), tabs switch, rows open panels, dialogs and drawers open and close. **An action whose real outcome is navigation navigates** — login lands on home with any input its fields accept — so the walk from login to the deepest page works end to end, with no auth, session, or validation logic simulated; a field's required and format attributes are markup, drawn as production carries them. Every interaction written here is real component code that survives promotion. A conditional branch interaction cannot reach cheaply gets its own frame (Coverage).

**Assume the product whole — expansion is a duty, not a permission.** Draft the full product (at Step 3, per SKILL.md) from `docs/product.md`, `docs/rules.md`, `docs/glossary.md`, and domain knowledge, page by page; `build-flow` Section 4's product-type research is its floor, never its ceiling. **A canvas that renders a thin brief as thin pages has failed.** Draw the full draft and **mark every improvised feature visibly as a proposal** (a small tag on its section). Ask the cut in the judgement call as a multi-select of what to remove — first option `keep all`, recommended, then one option per feature with a one-line description, more questions in the same call past four. Remove what is ticked. A kept proposal carrying a business rule the documents lack becomes a `docs/rules.md` line put to the user, per `docs-format`; one carrying none is recorded by its page alone.

**Where UI exists, the brief's floor is the function inventory from `handover.md`, never the pages.** Re-allocate functions freely — another page, the chrome, merged, shrunk to a line; never redraw as page content what the new chrome carries. Only a function absent from **every** canvas page is a cut, asked at the judgement, never silent. Still improvise and reshape shells, tagged — redrawing today's pages in new tokens is a repaint and has failed.

**In a redesign, the current design is not an input — and `DESIGN.md`'s prose is the current design.** Its visual-direction prose, signature, ornament rules, and archetype shell column are not constraints; redraw a signature only because the new direction earns it, tagged. The audit's numbers price the pass and power the before/after, never anchor the direction. **The blindness is enforced by distance**: only the audit subagent opens the old UI (SKILL.md Step 1); the drawing session works from `handover.md` and the answers, opens no file of the app beyond `docs/product.md`, `docs/rules.md`, `docs/glossary.md`, `CLAUDE.md`, and the data-layer files `handover.md` names, and never reads the dependency file. **The one exception is a value the user chose to keep** (`interview.md`, What the designer settles; SKILL.md Step 5, a Keep pick carrying a change): that value alone is read from the styling files.

A reference the user points at — ticked, named under Other, or arriving later as a file, screenshot, or URL — is inspiration only, **unless the user stresses it in their own words** (`interview.md`); only a stressed one is measured against at the judgement.

**Measured, never transplanted.** Never import a reference's code, copy its components, or reproduce its visual identity; refuse imitating a company's distinctive UI however worded. Where it is reachable, **look at it and take the numbers off it**: density, type character, colour temperature, motion budget. Unreachable, or reachable with no screen of the product → say so, and say the direction is drawn from memory.

## Asked before drawing

The interview and install gate run per `interview.md` and SKILL.md Steps 3–4; packages exist before any frame is drawn. Where UI exists, a value meets the one it replaces only at the gate (SKILL.md Step 6), which the drawing session reaches with its blindness over.

**Assumptions are declared before drawing, in one block — mandatory.** After the pick and before its first canvas file, list every product and behavior call no answer, function-inventory line, or data-layer file settles — layout calls, invented sections, data assumptions, conditional behaviors — one line each (`bottom bar: 3 slots, input as the primary action`). Never list visual values; they are read at ratification. The block is a cancellable derived-decision report, not a gate; its lines return at the judgement call, attached to what they produced.

## Directions first — the default, not the exception

**The frames run in every session, without exception**, after the install gate — the canvas's first round. **Nothing about the look is asked after them**: the picked frame is the direction, its values read at ratification.

Draw **2–4 direction frames**, composed per `interview.md`, each naming its source in its motivation line. **Two screens per frame: the proving page, and the screen of a second archetype the direction is most likely to break on next**, both answered at the interview, each in its populated state. Never the whole app, never posters. Hold **the proving page** through the flow: promotion moves it first and `build-flow` judges later pages against it. Draw in the answered theme mode — **only where the theme-mode answer was `Decide for me` may one frame use the other mode**, where its direction only exists there, saying so in its motivation line; picking it settles the mode.

**Full fidelity.** Type, colour, spacing, real copy, real fixture values — never grey boxes; bland is what this step catches. **Type included**: each frame picks its own faces and loads them by link; the picked frame's pairing is the app's typography from then on, and its package, where one is needed, is installed at ratification.

**Drawn in the canvas's own format, in place, with the installed stack**: files under `src/design-canvas/` named `<page>.<candidate>.tsx` (the platform's own page format off the web), controls from the chosen library, viewed on the running route and screenshotted at both widths (Judging). No second format and no later swap exists anywhere in the flow.

**A frame is a sketch in the final format; the production duties wait for the pick.** Until the pick each frame is **one file per screen and one stylesheet of its own**, and owes only what the user judges: full fidelity, real copy, realistic data whose numbers close, a candidate signature, tagged, the render scan, `impeccable`'s floor, `ui-ux-pro-max`'s UX floor, `review-animations`' floor where installed, the accessibility floors, the platform rules. It owes nothing the user cannot see: no shared component file, no cross-frame control pattern, no contract-shaped fixtures file, no production token names or alias layer, no unshown state, no state hook. Values are raw in the frame's stylesheet and data inline — with Tailwind, raw arbitrary-value utilities, the stylesheet holding only font loading and keyframes. **Where *own components* was chosen, each frame draws its controls in its own anatomy**, or the directions differ by token only.

Four rules make the set a real choice:

- **Each candidate explores an axis that can be named** — *Warm editorial* against *Dense data-first*, never variant A against B, never five shades of one aesthetic.
- **Each candidate carries an honest motivation and its main trade-off**, one line each.
- **Names are stable** for the rest of the session — never renumbered or renamed, including across a regeneration.
- **One is marked as the recommendation**, with a reason from this app.

**The design plan runs after the pick, never before** (SKILL.md Step 5). Announce nothing beforehand beyond each frame's motivation and trade-off lines — no palette, pairing, or signature.

**The pick dialog** is one AskUserQuestion, single-select, asked with the frames on screen: the running route, each frame's two-width screenshots, and **one side-by-side capture** from the entry route's compare page — every frame file in an iframe at the desktop width, the Keep candidate at its real route — handed over before the question. **Where Keep is a candidate, a subagent takes the Keep captures and the side-by-side and returns only their paths**; the drawing session hands the paths over without opening them or the compare page. No subagent available → the side-by-side shows the frames alone, and the user opens Keep's real routes themselves. Read an Other answer carrying a correction (*the second one, but with the brand green*) or a mix (*the layout of the first with the palette of the third*) as that frame with the change attached. **The question text says how to reject the set**: *none of them — type what is wrong under Other and I draw another set*. **Reject-the-set** deletes the set and redraws one fresh set to what was said wrong, under the same rules; a second rejected set opens the escalation. The pick is not a correction round.

**One refine round, only when the pick carries a change.** A clean pick goes straight to the design plan. A correction or mix is redrawn once — both of the picked frame's screens with the change applied — shown at both widths and confirmed with one AskUserQuestion: use this · adjust it once more · back to the set. *Adjust it once more* runs once; then the plan follows whatever stands. It is not counted as a correction round. **The unchosen frames survive until this round closes**; then delete them, their screenshots, and the compare page.

**The chosen frame is carried into the canvas, never redrawn from nothing.** Rename it to its real page's name, then **refactor** it: raw values into canvas variables under production token names, held to SKILL.md Step 6's five rules, controls into the shared set, data into the contract-shaped fixtures file, every state drawn, the three scans run. **The refactor is proven on screen before any other page is drawn**: capture it at both widths beside the picked frame's captures, taken after its last change — pixel diff where a tool exists, side by side otherwise — and fix any visible difference now, whichever side reads better. Change only by addition, plus the correction attached to the pick. A departure large enough that the page no longer reads as the picked frame is a line at the judgement, never a silent redraw.

**Nothing stands the frames down** — not a stressed reference (it gets its own frame), not a brand palette (a constraint every frame is drawn under, colour derived per `impeccable`), not Keep (today's look is one of the frames, the running app at its real routes, never redrawn), not a user who seems to know what they want.

## The canvas file

**One folder, one file per page.** `src/design-canvas/` beside the design-system route: one TSX file per page (off the web, the platform's page format and source layout, same rules), **named exactly as its real page is or will be named**, plus an entry route landing on the primary role's landing page (the chrome's nav is the page list; the route shows the compare page while only frames exist, and the first canvas page until that landing page is drawn) and one CSS file carrying the canvas variables. Dev-only like `/design-system`, out of navigation and the production build. Never one monolithic file, never files outside the folder. **A file more than one page imports — a shared wizard, a shared card — names its production path in its own header line, decided the round it is created, and enters the pass's file plan as its own line.**

**The canvas is the final front-end, staged.** Write every file after the pick production-grade: real library components, production token names, and **every state drawn** — loading skeleton, empty state with its wording, failed, busy — since a state added at promotion is markup the user never approved. **Fixtures live in one file, shaped as the data contract** the real layer returns — `build-flow`'s contract shape where no data layer exists, the existing modules where one does. Promotion swaps one import; the only legitimate difference between a canvas file and its live page is the data. Cases and roles are reached through `build-flow`'s two switches (`contract.md`).

**Every page, drawn.** Derive the archetype table first, grouping pages per `interview.md`'s archetype rule; where UI exists the **grouping** comes from the existing routes, and that is all the old app contributes. **Propose each archetype's shell fresh** from the picked frame, the brief, and your judgement — never read an existing page to learn its shell; today's shell reaches the user only as the audit screenshot paths the judgement's shell report hands over. Draw **every page** to its archetype's shell — content from the function inventory where UI exists, from the documents where it does not.

**`/design-system`** is generated before the frames, per SKILL.md Step 6. Nothing on the canvas depends on it. **Where UI exists and the route already renders the old theme, leave it alone until ratification and never look at it**; an app with no route waits for the pass (Step 7).

**Quarantine, both directions.** Nothing in the app imports the canvas; the canvas imports only from the **declared UI stack** — the chosen component library, the chosen icon pack, the engine libraries the dependency file carries for UI jobs (charts, table engines, date pickers, drag-and-drop), and the packages their install documentation names beside them — and its own CSS, plus type-only imports (`import type`) from the data-layer files `handover.md` names, or from the contracts where no UI exists. Never the production theme, tokens, or components. **A copy-in library (shadcn and kin) enters the canvas as a fresh copy from its registry** under `src/design-canvas/ui/`, the CLI's path option verified live and the copy's internal imports pointing at the copy — never imported from the app's components folder, which carries today's look; promotion replaces the app's copy file for file. The app must render identically with the canvas deleted.

**Real components, canvas-owned theme.** Library components render inside a scoped theme wrapper carrying the canvas's values (CSS variables on the web) — where the library portals overlays out of it, on the portal's root too, frames included. **Element selectors in the canvas CSS style native controls only** — scope them out of library components (`:not([data-slot])` or equivalent) the moment a native control is swapped. **Draw every control the chosen library ships with the library's component**, from the first round. Hand-roll only where the library has none for the job, each as its own line in the judgement call. **The rule governs the control, never the composition**: compositions of primitives and domain components no library ships — a ledger row, a shift strip — are the canvas's to invent; stock components alone is the generic outcome. Extract a component appearing twice under `ui-build`'s reuse rule. **With *own components*, every control is the canvas's own and none is a line**; a second form of one control across pages is the finding.

**The declared stack binds the engines too.** Draw a job an installed engine owns — chart, virtualized table, date picker — with that engine, never re-implemented beside it. Hand-rolling where an engine covers the job is a departure line at the judgement (`recharts installed → drawn as CSS bars, because Z`); swapping or dropping an engine is an explicit user decision there, and an approved swap becomes its own install/remove line in the pass. An engine need that emerges while drawing follows `engine-rubric.md`: draw the no-engine rendering tagged, settle it at the judgement, and on approved adoption install and redraw that frame next round.

**Before each round is shown, run three scans; a round that fails any is not ready to show:**

1. **Imports.** Every control maps to a library component, the canvas's own shared set (*own components*), or a named hand-rolled line; every engine import comes from the declared stack.
2. **The render.** Run `impeccable`'s detector against the round's running routes (its URL tier) and fix the defect class — clipped or overflowing containers and text, occlusion, broken images, script errors, an attribute the source writes (`aria-*`, `role`, `href`) missing or rewritten in the rendered page, an accessible name (a library's own included) not in the app's locale (`ui-build` names where missing library strings come from). **Act only on defects in a round**; a hit that judges the direction (nested containers, uniform spacing, a colour family) travels to Step 8. **Read every capture of the round yourself before the user does**, detector or not, and fix clipping, overflow, occlusion, and labels that lie (a size label the frame does not show, an animated state a still renders as nothing). Never use this scan to re-open composition.
3. **The arithmetic.** Compute every number printed as a claim — ratio, percentage, count, total — never recall it, and make the fixtures close (Coverage). Count the copy too: cut every string on a tenth-use page over `ui-build`'s copy caps, the direction frames included. Read the assumption lines against each other and the fixtures; a contradiction is fixed before the round is shown.

Report the scan with the round as a short list of what it caught and fixed. **Where UI exists the scan covers the fixtures too**: take value types and field names (enums, state labels, column names) from the existing contract or data-layer modules, and never redefine an existing type name with different values. Do not import page-structure types — filter shapes, page sizes, and query keys stay the canvas's to redesign. Draw a field with no source in either tagged as a proposal.

**The taste license, granted explicitly.** Design with a free hand. The licence owns outright everything the picked frame did not settle — palette steps, surfaces, elevation, type scale, spacing, every other page's composition. What the user settled — the pick, its correction, a named reference — is their **preference — the baseline, not a cage**, and **departing is part of the job, not an exception to argue for**: draw the better call, tag it, and list every departure in one cancellable report printed above the judgement call, one line each shaped `picked X → drawn Y, because Z`. A cancelled line reverts to the pick; the rest enter ratification.

**The licence covers `frontend-design`; `impeccable` is the floor it stands on.** Depart from any `frontend-design` value — a palette count, a family count, a composition habit — only drawn, tagged, reasoned in one line, and settled at the judgement; never silently. `impeccable`'s Refuse list, Verify list, calibrations, and detector bind every round as written: a Refuse-list hit is fixed, or stands at the judgement as a finding under the detector's own name; a face on the calibration list is chosen only with its reason written in the design plan. A detector hit stands on its own rule whether or not a calibration list names the value; a hit the library's own stylesheet or component anatomy causes stands as a finding with that reason — never restyle the library to silence it. No direction departs from `interview.md`'s floors — contrast, colour never the only marker, reduced motion honoured, a visible label for every field, the platform's touch targets — nor from this file's engineering rules: quarantine, token names, fixtures that close, one-to-one promotion.

**The licence carries a duty: one signature.** Every canvas draws a **single element this app is remembered by** — a treatment, a shell move, a way one recurring thing is rendered — where the boldness is spent; everything around it stays quiet. Never three competing signatures, never none. **Tag the signature on the canvas like a proposal**; it is settled in its own question (Judging). `frontend-design` holds the method for choosing the direction it serves.

**The material** — `impeccable`, `frontend-design` and `ui-ux-pro-max` as ruled below, plus `review-animations` where installed — is loaded before the interview per SKILL.md Step 1 and stays in hand for the design plan, every round, the judgement, and ratification; never re-read step by step, except at the escalation. Each is guidance, never an authority: where one collides with a user answer or a ratified value, the user wins.

**What crosses from `impeccable` — named by role, located through its own `SKILL.md` index at load time, never by a remembered file name.** **Crosses:** its **craft floor** — the Refuse list, and the Verify list as a build-time check; its **two calibrations for new work** — the overused training-data display faces and the clusters AI interfaces converge on; its **operational register** entire **on an operational app**, never on a landing page. **The Refuse list crosses by what it forbids, not by the CSS it names**, so it holds on a Surface with no selectors. **Does not cross:** its **direction pipeline** (interview, dice roll, decision server, comps) and its **agents** — spawn none; `docs-format`'s list stays the only set of documents. **Never run an `impeccable` command that writes `PRODUCT.md` or `DESIGN.md` from the built world** (`init`, `document`, `extract` at the time of writing); answer its `init` offer by pointing at `DESIGN.md`. **The one `DESIGN.md` is the one SKILL.md Step 6 writes.** Report a role `impeccable` no longer carries at the Design material row; never invent it. **The detector reads HTML and CSS, so it runs only on web technology** — web UI, or a Tauri, Electron, or Capacitor shell. On a **truly native** Surface (SwiftUI, Compose, XAML and kin), skip every detector instruction in `design-settle` and report `n/a — native surface`, never a zero; those steps' checks come from the Surface's Proof profile.

**A native Surface gains `impeccable`'s platform references in the detector's place**: load its iOS and/or Android reference (both on an adaptive Surface) alongside the craft floor. Web technology loads neither. **A desktop Surface — shell or native — is researched, not referenced**: before the frames, WebSearch the target OS's current design guidelines, vendor documentation first — navigation model, window chrome, control sizes, type ramp, materials, accessibility floors — and name the sources in the Design material row. WebSearch unavailable → say so there, draw from model knowledge, and mark the platform rules unverified. **On macOS, `apple-design`'s pages are read first where installed** (`apple-design/SKILL.md` under `~/.claude/skills/` or the repo's `.claude/skills/`): the macOS ones and those for the controls the frames draw, located through its own lookup index, plus its cross-platform translation on a non-Apple stack — never its review mode, craft lens, or always-load set. WebSearch covers what they leave open.

**Two `impeccable` playbooks route by platform the same way:** read its **audit** playbook (accessibility, performance, theming, responsiveness, implementation integrity, touch-target floors) or its **adapt** playbook (width and device-class rules) in the web or native variant matching the Surface, when a step needs one; its other playbooks stay out.

**One collision, decided here:** where a ratified `DESIGN.md` line contradicts `impeccable`'s OKLCH colour derivation, `DESIGN.md` wins, as it does over every line in this file.

**What crosses from `frontend-design` depends on the Register switch — first visit or tenth use** — derived at `app-settle` question 1 and re-derived from the Roles whenever read. **Tenth use** (a tool people return to): take **the calibration**, **the two-pass method** (state the plan, critique it against the brief, say what changed), **the signature**, and **the restraint** (spend boldness once, then remove one thing); leave the marketing anatomy — **the aesthetic risk is the signature and nothing else**, never a posture that costs speed of use. **First visit** (landing page, marketing site): **the whole file crosses** — hero as thesis, landing anatomy as the brief's floor, a posture across the page allowed; the signature is still asked on its own, and calibration and restraint still bind. **Both registers** in one product: first-visit on public pages, tenth-use behind the login, per page group. `impeccable`'s floor applies whole on every branch.

**`review-animations`, where installed, binds motion in every round on a web-technology Surface, as `ui-build` defines it**: an animation it forbids is fixed, or stands at the judgement as a finding under its name — the standing of a Refuse-list hit. A native Surface takes motion from `impeccable`'s iOS or Android reference, or from the desktop research above, instead.

**Never load a skill that names the look as material** — a fixed palette, pairing, card recipe, or shadow scale. Always load guidance that **narrows the space the look is chosen from** — the generated-looking defaults, the two-accents-one-family formula, the failed-choice typefaces. **`dataviz` is loaded for its method alone**: its palette is never used; the chart palette is `DESIGN.md`'s (SKILL.md Step 6).

**What crosses from `ui-ux-pro-max`.** Its generator and look searches name a look, so they enter only as frame ingredients (`interview.md`), never as a rule a round is held to. Its UX and stack guidelines are the floor level with `impeccable`'s, as `ui-build` rules them: a don't they name is fixed in every round, or stands at the judgement as a finding under its name. Read its `design-system` references on token architecture and component states before the refactor after the pick; Step 6's five rules win over them. Its chart search picks a chart type only, never a colour.

**The canvas carries its own foundations board, as a page of its own** — palette roles and steps, text scale, spacing, radius, shadow, status triads — rendered from the canvas's variables. The entry route never lands on it. The board is its own nav entry **set apart from the page groups**, and **renders inside the same chrome shell as every other canvas page**.

**Show a token applied to itself, every other variable held constant. Never a table row.**

- **Spacing**: a square that many pixels, steps side by side as a staircase; floor the drawn size so a degenerate value still renders a labelled marker.
- **Radius**: identical tiles differing only in corner.
- **Shadow**: identical surface tiles that actually cast, with vertical room so the shadow is not clipped.
- **Border width**: identical tiles differing only in stroke.
- **Colour**: fixed-size swatches carrying step name, resolved value, and the semantic alias pointing at it, with a hairline inset ring so near-white steps keep an edge. **Grouping is carried by the gap** — tight within a ramp, looser between families.
- **Type**: every step shows **a different real sentence from this app's domain** — the one it carries on a screen; one repeated neutral string only on the weight specimen.
- **The alias layer gets its own row**: role, step it points at, resolved value.

**Every specimen carries a caption in one identical treatment across the board** — monospace, muted, small — printing the token key **and** resolved value (`lg · 8px`, `hairline · 0.5px`). Relabel an absurd literal (`full`, not `9999px`).

**The board carries the contrast section** — one row per pair Ratification defines, in every ratified theme mode: a live chip of the real foreground on the real background, the computed ratio beside it, and its mark against the 4.5 / 3.0 floors (numbers per Ratification).

**The canvas's variables carry the production token names** exactly as the theme files will name them, so ratification is a copy, not a translation. **Where the styling answer is Tailwind**, canvas utilities read those variables and ratification moves them into the production Tailwind theme under the same names — look the syntax for both up for the installed Tailwind version at write time (WebSearch; the package ships no docs), never recalled. **Where a class-merging utility is in the stack, register the production token names with it** before the first canvas file uses them, or it drops them. A utility internal to the library, outside the import whitelist, cannot be registered: name tokens only in shapes it already classifies — t-shirt sizes (`sm`, `md`, `lg`).

## Coverage

**Coverage.** Show the whole visual language once across the pages: every colour role on real surfaces · text steps on real sentences · the densest data view with messy fixtures (long labels, large numbers, missing values), if any · form controls in their states · **every conditional branch of a form as its own frame — a status that reshapes the fields (deal / no deal) is two frames, never one with a note** · status markers · one card or KPI group · **the busy state of every long-running operation — import, matching, bulk delete — as its own frame with real counts** · the loading, empty, and failed state of every page that has one · the behavior at both widths. Realistic domain data from `docs/glossary.md`. Rows no source holds — a `bulk` case the replaced process never reached — are synthetic and named so (`contract.md`).

**The numbers must close** wherever figures were invented rather than copied from the document the app replaces (`contract.md`). On every page:

- A headline total equals the sum of the parts beside it; a remainder equals the difference it claims.
- A percentage, ring, or progress bar equals part over total to its displayed precision.
- A top-N list sums to less than its headline.
- A bar width is **computed from the value printed next to it**, normalised against the largest in the set — never typed.
- A pagination label's range matches the rows rendered; its last page equals total ÷ page size, rounded up.
- A sort affordance's direction matches the data's order.
- One fictional record named in two places is named identically.
- Totals are **derived from the fixture array**, never typed as literals; a total larger than the rows shown is declared once in the fixture and every figure derived from it, never padded with rows nobody sees.

Numbers, dates, thousands separators, and currency follow the app's locale per `CLAUDE.md`'s Locale row.

**One pattern per recurring control.** Row actions, pagination, summary bars, filter rows each take exactly one form across every page — the active page visibly marked, the same action affordance on every table. A second form is a finding at the judgement. **Fixture text and labels are written in the user's language**, as on production screens.

## Judging

**The platform is proven, not assumed — as a list.** Off the web (the Surface row), put the canvas beside one real native application — the picked frame's source where it is one, else one named here — and list the differences: window chrome, navigation shape, control size and radius, icon family, type, accent. Settle each as a **departure** with its one-line reason or a **correction round**. "It looks native" is not an output.

**The same list runs on any platform when the picked frame was drawn to a stressed reference** — stressed in the user's own words, never only ticked or chosen by Claude: density, colour temperature, type character, motion budget, shell shape, how a recurring control is rendered, each settled as a departure or a correction round. Where the reference is not a product, list what can be measured — colour, type character, material, a marker or shape — and name the rows that could not be written. *Measured, never transplanted* still holds.

**Screenshot at two widths**: `DESIGN.md`'s desktop breakpoint (1440px where none exists yet) and the derived lowest supported width, with the session's browser tooling. A width below the browser window's minimum (near 500px) is captured by emulating a mobile viewport of that width (Chrome DevTools' `emulate`), never by resizing the window. A page longer than the browser captures is captured in viewport-height segments. **Where the reading or the Proof profile names users on iPhone, iPad, or Mac, capture both widths in WebKit too**, the narrow one as an emulated iPhone; no WebKit tooling → `not verified — WebKit`. Where the Proof profile names something other than a browser, capture through its Visual line — same two bounds or the platform's equivalent.

**Shown inside its device.** Present the narrow capture inside a phone frame and the wide one inside a window frame. **No fake chrome inside the frame** — no painted status bar, keyboard, or fake tab strip carrying content. **The frame belongs to the entry route, never a page file.** With no capture tooling, report the run target and both widths; draw no frame around nothing.

**Two correction rounds per canvas**, a correction round being one opened by the user rejecting what was drawn; a third does not run — the escalation opens. A round opened by the user **asking for something new** is not counted and quotes the request it serves; a round that cannot quote one is a correction round.

**Escalation decides values, not pixels**: its answers become the brief's constraints, and the canvas is **regenerated fresh**, never patched, under the same two-round rule. **Regeneration replaces the direction, never the decisions**: every approved feature proposal and every ratified shell carries into the regenerated canvas.

**Every decision in this path goes through AskUserQuestion**, under `interview.md`'s rules. **Write every label in the words the user uses, never this file's** (*ratify*, *seam*, *archetype*, *departure*); say the action: keep this value, delete this page. **The judgement call** holds: a single-select verdict (approve · rework this round · escalate to the questions), the marked-feature multi-select, the assumption lines, the hand-rolled-control lines, and the shells — one report, each archetype's new shell in a sentence, where UI exists beside the audit screenshot paths of its routes, never a description of the old shell this session has not seen, **whether it departed or not**; where it does not, only the archetypes the user's archetype-table correction did not already settle — then one multi-select of the shells to redraw, first option `keep all`, recommended. Four questions per call; more means a second call in the same turn. Ask contrast failures, cancelled value lines, and reopened questions the same way.

**The signature is its own question, asked on its own** — one AskUserQuestion naming the element, saying what it costs the pages around it, offering keep · redraw it once · drop it and accept the quieter page. Never an item riding the verdict call. A rejected signature is redrawn once; only the user drops it. **In Fast, the judgement call and the contrast stop below run as `SKILL.md`'s Fast or Full says.**

**Two more lines join the departure report whenever they exist**: the **reference differences** against a stressed reference · the **direction candidate** the user picked, named, so later rounds cannot drift off it.

## Ratification — approval happens on the canvas, the values follow as a report

**Approving the canvas is the approval.** Then read the values behind it, library-rendered ones included — palette and steps, type scale, spacing, radius, shadow, density numbers, and the picked frame's source (recorded in `DESIGN.md`'s Overview) — and report them as derived decisions, one cancellable line each; a cancelled line reopens that value as a question. No second gate over the same pixels. Two cases still stop:

- **Contrast — computed, never recalled.** **Calculate** every pair — each foreground on each background it renders on, a library's calculated slots and chrome compositions included, a pair `DESIGN.md` forbids excepted — in every ratified theme mode, with the WCAG relative-luminance formula — never from memory or by eye — where the board renders, so numbers and chips share one source. **Choose each semantic family's dark shade by measuring it against its own light shade until it clears 4.5**, never by stepping along the ramp. Put a failing pair to the user, never silently passed or fixed; a passing pair still prints its number.
- **Where UI exists.** The values enter SKILL.md Step 6's gate as the *new* column of the diff; that line-by-line approval is the one gate.

Writing `DESIGN.md` and the styling files follows SKILL.md Step 6.

**Promotion — the canvas is the reference, and approval promotes it.** Copy each file to its real path — **the proving page first** — remove the canvas theme wrapper and the canvas-only instruments (proposal tags, canvas nav entries), and replace the fixtures with the real data layer per `build-flow` and `logic-settle`. **Copied means the canvas file becomes the page**; a production page re-tokened from its old markup is not promoted.

- **Element-for-element.** Every visible element survives into the page (fixtures swapped for data, real states added) or appears as a named deviation line at the recap with its reason — real behavior contradicts the drawing · the backend does not exist yet · the control is obsolete. Never substitute a plainer equivalent silently (a bare file input for a drawn dropzone). A canvas control the real flow never had is a canvas error reported for the user's decision, never quietly dropped.
- **The proof is a diff, not a look.** Differences between canvas file and promoted page are confined to the data seam (fixture import swapped, plus loading and error wiring) and approved deviation lines; any other difference is a failed promotion to fix, whichever side reads better. **Before its data swap, pixel-diff each promoted page on the canvas fixtures against its canvas file** at both widths, with a diff tool run outside the app's dependencies, the diff images kept for Step 8; a differing pixel outside the removed instruments fails the promotion; no tool → `not verified — pixel diff`.
- **Foundations first.** Everything the canvas CSS carries beyond token values — font loading, element rules, shadows, motion durations — and every setup file the canvas relies on (a class-merge registration) lands in production before any page moves, verified by computed style that fonts resolve to the loaded webfonts, not a fallback (off the browser, through the Proof profile's Visual line, naming what could not be verified).
- **Shared chrome first.** Each shared chrome component a canvas page imports lives in production before any page importing it counts as moved.
- **Survival of real data**, per page at both widths: a layout collapsing under real rows, a token that did not land, or a vanished section stops the pass as a rework round of that page, two at most before `DESIGN.md` reopens. Real rows differing from fixtures is not divergence.

Where no backend exists, promotion keeps the fixtures in `build-flow`'s contract shape and wiring arrives page by page through the queue; where a data layer exists it is wired in the pass. `/design-system` embeds no page — the app itself is the composition.

**The canvas lifecycle.** A ratified canvas file outlives its promotion as a frozen reference, and dies with its page's real implementation — never before. Never delete unasked.

- **Frozen.** Never edit a ratified canvas file again, and never use it as a source of values or patterns — `DESIGN.md`, the theme files, and the promoted page are the sources.
- **Deleted per page, beside the proof — and only with the user's word.** The session that wires a page with real data and sees it survive both widths compares page and canvas file, fixes silent divergence, then **proposes** the deletion at a chat stop — naming the page, inviting the side-by-side look, ending the turn, never through AskUserQuestion — and deletes only on a granted confirmation. `build-flow` carries this for pages wired later; where the pass wires in-session, one confirmation at its verification step covers the whole canvas.
- **Remnants go last.** Delete the entry route, the foundations board, the canvas CSS, and `.design-audit/` when the last page file goes.

## What the canvas never decides

Page content (`build-flow` Section 4) · the archetype table — the canvas proposes every shell, but the table becomes real only through the user's archetype-table correction and the judgement's shell answers · loading, empty, and error norms (`ui-build`) · anything the user does not ratify.
