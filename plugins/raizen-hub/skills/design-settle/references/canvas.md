# The design canvas — taste decided on a free page, not by questions

One temporary TSX route — **every page of the app, redesigned** — where the visual direction and every shell are designed whole, judged in the real browser, then ratified value by value into Section 5. It replaces the long tail of taste questions a long-form interview would ask — everything beyond the taste batch; it never replaces the batch itself or the stack questions.

## When this path runs

- the fresh path, after the taste batch and the stack questions of `interview.md`. The direction frames below run earlier than that, inside the interview itself.
- the rework path's overhaul, the same flow with keep-first slots.

**Escalation when the canvas misses twice:** the whole interview re-opens in its own order — the reference slot again first, with products chosen against what was rejected, then **a fresh set of direction frames** unless that answer pins the direction, then every remaining slot re-asked with sharpened options built from what the two rejections taught — and the canvas is regenerated fresh from the new answers. The frames are redrawn rather than reused: the two rejections are the sharpest material this session has about what the user does not want, and a set that predates them has not heard it.

**`taste.md`, `impeccable`, and `frontend-design` are re-read before those options are written.** This is the only point in the flow where options are written twice, and the second time is the furthest the session ever gets from the material: two canvas rounds, a full product draft and a judgement now sit between the first read and this one. Options called *sharpened* but written from a decayed memory of the material are the first batch again under a new name — which is precisely the failure that opened this escalation. The re-read costs one read and is the cheapest part of the whole escalation.

## The brief — features in, interpretation free

The input to the canvas is the **user's feature list**, plus what the PRD already holds. The user names what the app does; the canvas decides how that looks — composition, richness, hierarchy are the designer's to interpret, and the user judges the result rather than pre-approving a layout.

Two bounds on that freedom, both the user's own condition:

- **Function is faithful.** A feature on the canvas shows what the feature actually does — its real fields, its real states, the figures a business rule demands. What stays forbidden is the **untagged** invention: an improvised feature drawn without its proposal tag, or promoted without ratification. Tagged improvisation is not the exception this rule guards against — it is the canvas's job, granted below.
- **It renders working — static data, live chrome.** Real fixtures, not lorem; states, not placeholders. The **data** is static by design: nothing fetches, nothing writes, no auth, no validation, no business logic — real behavior arrives when pages are built through `build-flow`, whose Bound list is where *matches the function* is enforced page by page. The **chrome** is alive: sidebar and menu items navigate between canvas pages (plain anchors to the sibling files — no router import, the quarantine holds), tabs switch, a row opens its panel, dialogs and drawers open and close, the collapse collapses — local state over fixtures, nothing more. **An action whose real outcome is navigation navigates too:** the login button lands on the home canvas with nothing checked and any input accepted, a work-queue line lands on the page it points at — the walk from login to the deepest page works end to end, and no auth, no session, and no validation is simulated to make it so. The user judges flow as well as composition, and a canvas that cannot be walked is judged as posters; every interaction written here is real component code that survives promotion. A conditional branch that interaction cannot reach cheaply still gets its own frame, as Coverage requires.

**Assume the product whole — expansion is a duty, not a permission.** Before drawing, draft the full product this brief implies: from PRD Sections 1–4 and the designer's own knowledge of the domain — what a mature version of this app would hold, page by page. The product-type research `build-flow` Section 4 draws from is the floor of that draft, never its ceiling. The user naming two features is an opening, not the ceiling — **a canvas that renders a thin brief as thin pages has failed its job.** Draw the full draft, and **mark every improvised feature visibly as a proposal** on the canvas (a small tag on its section). The cut is then **asked, not narrated**: in the same AskUserQuestion call as the judgement verdict, the marked features form a multi-select — every feature an option with a one-line description, keeping all as the recommendation; four options is the tool's cap per question, so more features means more questions in the same call. What is unchecked is removed. Same bias `build-flow` applies per page — propose the full thing, let the user trim — but here the proposal arrives rendered, because a feature is easier to judge on screen than as a line in a list.

A kept proposal the PRD does not yet hold is reported as a PRD line for the user's decision, per `prd-format`: the canvas may show it, only the PRD makes it real.

**On the rework path the floor of the brief is the app's function inventory, never its pages.** The audit reduces the existing pages to a written inventory — every function the app carries, one line each, page-agnostic — and that list joins the brief as given. What a page currently *holds* is not in the inventory: "session identity as a card on home" is an allocation the old design made, and the new direction re-allocates freely — a function may move to another page, into the chrome, merge with a neighbour, or shrink to a line. A function the new shell's chrome already carries is not drawn again as page content out of loyalty to where it used to live. Only a function absent from **every** canvas page is a cut, and a cut is asked at the judgement, never silent. Improvised features and reshaped shells are still expected and still tagged — a canvas that redraws today's pages in new tokens is a repaint, and a repaint has failed the job. *Function-faithful* binds what a shown feature does; it never binds a layout to what the layout used to be, nor a function to the page that used to hold it.

**In a full overhaul, the current design is not an input — and Section 5's prose is the current design.** What the app *does* joins the brief as given; how it *looks* today does not — the canvas is drawn as if the app had no visual past, from the answers and the license below alone. That blindness covers the document, not only the code: the old Section 5's visual-direction prose, its signature, its ornament rules, and its archetype shell column are today's design written down, and the canvas may not read them as constraints. A signature worth keeping is re-drawn because the new direction earns it — tagged like any improvisation — never because a ratified sentence demands it. The audit's numbers exist to price the pass and to power the before/after at the judgement, never to anchor the new direction. **And the blindness is enforced by distance, not willpower:** the old page files are opened once, at the audit, to write the function inventory — the drawing phase works from that inventory and the answers, and does not reopen them; the Step 1 screenshots serve the judgement's before/after and the Step 9 comparison, and are not looked at while drawing. A rule that says "don't treat it as input" while the input sits freshly read in context is a rule that loses.

A reference the user points at — answered at the taste batch's own reference slot, or arriving later as a file, a screenshot, or a URL — is welcome as inspiration for the interpretation, and a named one becomes an anchor this canvas is measured against at the judgement (Judging, below).

**Measured, never transplanted.** What stays forbidden is moving its machinery across: importing its code, copying its components, reproducing its visual identity — a reference sets the direction, never the reproduction, and imitating a company's distinctive UI is refused however the request is worded. What is expected is the opposite failure's cure: where the reference is reachable — a screenshot the user attached, a public page the session can open — **look at it and take the numbers off it**, so density, type character, colour temperature and motion budget come from observation rather than from a memory of the app. Unreachable → say so, and say the direction is being drawn from memory; that sentence is what tells the user how much weight the anchor can carry.

## Asked before drawing

The taste batch and the stack questions of `interview.md` — the reference slot alone, the direction frames it routes to, then six or seven slots in one turn, then the component library, its icon dialog when the library bundles none, and any engine dialog a trigger fired. Answered slots set the canvas's baseline; slots answered "Decide for me" are the canvas's own. On the rework path every slot carries a `Keep — <today's value>` option, written first but never the recommendation — the library question alone recommends keeping the installed library, unless the audit indicts it.

Install per the skill's own install step **before** the canvas is written. The canvas is built from the real packages, so they must exist.

**Assumptions are declared before drawing, in one block — mandatory, never skipped.** Every product and behavior call the canvas makes that no answer settles — layout calls, invented sections, data assumptions, conditional behaviors — is listed one line each (`GPS tolerance shown as a badge with live distance` · `bottom bar: 3 slots, input as the primary action`) before the first file is written. **Visual values are not assumption lines** — palette, type, spacing, radius live on the canvas and are read at ratification; listing them here would report the same decision twice. The block follows the derived-decision pattern: a report the user may cancel line by line, not a gate that waits. The same lines return at the judgement call, attached to what they produced, where the user settles them through AskUserQuestion like every other canvas decision.

## Directions first — the default, not the exception

**The frames run in every session except the two where the direction is already pinned.** They are drawn once the reference slot is answered and **before the rest of the taste batch**, so every remaining slot is written against a picture the user has already chosen instead of against a description they had to imagine. *Dense data-first* against *Warm editorial* as two lines of text is not a choice a junior developer can make; the same two on screen is the sharpest judgement they make all session. **Where the frames run, the Direction slot is not asked** — the frames are what it is answered with.

Draw **2–4 direction frames**: each one a single representative screen of this app — the most data-dense screen of the primary role, where the PRD names one. Not the whole app, and not a set of posters.

**They are drawn at full fidelity.** Type, colour, spacing, real copy, real fixture values. The details are the decision: everything that makes an interface read as generated lives in exactly that layer, so a grey-box sketch hides the only thing the user is being asked about. A wireframe can answer whether the boxes sit in the right places; it cannot answer whether a direction is bland, and bland is what this step exists to catch before a whole canvas is built on it. **Type included:** each frame picks its own faces and loads them itself — no install is needed to put a webfont in a canvas file — and the picked frame's pairing then becomes the Typography slot's first option and its recommendation, so nothing the user already approved on screen has to be re-argued as a name in a list.

**What draws them depends on the path.** On the rework path the component library is already installed: the frames are TSX under `src/design-canvas/` and use the library like any other round. Nothing below changes them.

**On the fresh path the frames are drawn as a Claude Design canvas** — the `design` skill, one `.dc.html` artboard per candidate, published as one artifact. Two things earn a second format at this step and nowhere else in the flow. The frames are hand-rolled either way, because no library is installed yet to draw them with, so nothing is lost by drawing them somewhere the library was never available. And the user can **change them by hand** — click an element, retype the heading, retune the spacing or the colour, Save — which is the one point in the whole flow where taste arrives as pixels instead of as an answer to a question. A direction the user has adjusted is a sharper input than one they merely picked.

**The `design` skill absent, or its canvas refused a publish → say so in one line, then draw the frames as TSX under `src/design-canvas/`, hand-rolled — what the rework path draws, minus the library.** Everything else in this step is unchanged; what is lost is the hand-editing and the read-back below. A session that loses them silently leaves the user believing they saw everything this step had to offer.

**The canvas is read back before anything downstream is written.** Once they have picked and saved, extract the artboards and put the chosen one beside what was published: **what the user changed by hand is the direction**, and it beats the frame's own guess wherever the two disagree. Each change enters the batch as the first option and the recommendation of the slot it belongs to — a retyped heading into Typography, a retoned surface into the palette — so nothing they already fixed on screen returns as a question. A change with no slot to land in becomes an assumption line, settled at the judgement like the rest. Skip the read-back and the edits stay on the artifact while the app is built from the version before them, which is worse than never having offered the editing at all.

**Each frame still carries one line saying its controls are redrawn with the library once the stack is settled.** Without that line this becomes the hand-drawn mockup whose fidelity dies in transplant, which *Real components, canvas-owned theme* below forbids for every later round.

Four rules make the set a real choice rather than a rigged one:

- **Each candidate explores an axis that can be named** — *Warm editorial* against *Dense data-first*, not variant A against variant B. Five shades of one aesthetic is no choice at all, and a set whose candidates cannot be told apart in a sentence has not explored anything.
- **Each candidate carries an honest motivation and its main trade-off**, one line each. A set where only the favourite gets a case made for it is a rigged vote, and the user reads the rigging.
- **Names are stable.** Once a candidate is *Warm editorial* it keeps that name for the rest of the session — never renumbered, never renamed, including across a regeneration.
- **One is marked as the recommendation**, with a reason from this app.

**The design plan runs after the pick and after the batch, never before.** The frames carry their own axes — rule two above already makes each one state its motivation and trade-off in a line — and that is the whole of what is announced beforehand: no palette, no pairing, no signature. A plan published before the candidates are drawn has decided the vote it is about to hold, which is the rigged set that rule forbids, and a plan written before the batch is answered is a plan guessing at density and type.

The choice is one AskUserQuestion, single-select, the frames on screen when it is asked — the running route on the rework path, the published canvas link on the fresh path, handed over before the question is put. What the user picks becomes the direction; the full canvas is then built to it under the rest of this file, and the unchosen frames are deleted rather than kept as alternatives. **This costs one round and it is not one of the two correction rounds** — nothing was rejected, a decision was taken.

**The chosen frame is carried into the canvas, never redrawn from nothing.** It is a full-fidelity screen of a real page of this app, so it becomes that page's first canvas round: moved into `src/design-canvas/` under the name its real page carries, then finished to the rest of this file — every state drawn, fixtures moved into the one contract-shaped file, the three self-check scans run. Redrawing a screen the user has already approved on screen throws away the one artefact this whole step exists to produce, and risks arriving at a page they liked less than the one they picked. Two things do change on the way in, and both are additions rather than repaints: on the fresh path its hand-rolled controls are swapped for the library's now that the install has run — the swap that its own honesty line promised — and the batch answers taken after the pick are applied where they departed from what the frame guessed. A departure large enough that the page no longer reads as the frame the user picked is a line at the judgement, not a silent redraw.

**On the fresh path the frame is transcribed rather than moved, and that distinction is the whole of the licence.** Its artboard is `.dc.html` and `src/design-canvas/` is TSX; no copy step crosses that, so the frame is rebuilt element for element — every value read off the artboard and carried across unchanged, the controls swapped for the library's as its honesty line promised, the user's own hand-edits carried with the rest. What stays forbidden is exactly what *never redrawn from nothing* forbids everywhere else: reopening composition, type, or palette while transcribing. A value that changes on the way across is a departure line at the judgement, the same as it would be on the rework path. **The screen the user approved is this step's specification**, and a transcription that quietly improves it has thrown away the artefact the step exists to produce.

**Two answers stand the frames down, and only those two.** A reference the user named *is* a direction, and drawing candidates against it re-opens a question they already closed — that session asks the Direction slot in the batch as before. A brand palette to follow does the same for colour and pulls the rest of the direction with it. Everything else draws, including a session where the user seems to know what they want: knowing it in words is what the frames are cheap insurance against, and a wrong guess here costs a correction round that redraws the whole app rather than three screens.

## The canvas file

**One folder, one file per page.** `src/design-canvas/` beside the styleguide route: one TSX file per page (on a non-web platform, the platform's own page format and source layout — the folder-as-quarantine, one-file-per-page, and naming rules hold unchanged), **named exactly as its real page is or will be named**, plus an entry route that lands on the primary role's landing page (the chrome's nav is the page list) and one CSS file carrying the canvas variables. Reachable dev-only like `/styleguide`, out of navigation and out of the production build. Never one monolithic file, and never files scattered outside the folder — the folder is the quarantine boundary, and its structure mirrors the app's real pages **so that approval is a promotion, not a rebuild**. **A file more than one page imports — a shared wizard, a shared card — is not exempt: it names its production path in its own header line, decided at the round it is created, and enters the pass's file plan as its own line.** Without that path there is no file to copy it to and no pair to diff, so the composition the user approved is re-assembled by hand from its parts, and every page built on it is a repaint.

**The canvas is the final front-end, staged.** Its files are not illustrations of the future pages — they are the pages, held in a separate folder only because the user has the right to reject them before they replace anything. That is why every file is written production-grade from the first round: real library components, production token names, and **every state drawn** — the loading skeleton, the empty state with its wording, the failed state, the busy state — because a state added later, during promotion, is markup the user never approved. **Fixtures live in one file, shaped as the data contract** the real layer returns — `build-flow`'s contract shape on the fresh path, the existing modules on the rework path, enforced by the scan below. Promotion then swaps one import and the markup body never changes: the only legitimate source of difference between a canvas file and its live page is the data flowing through it.

**Every page, drawn.** Derive the archetype table before drawing — group the PRD's pages as `interview.md`'s archetype rule describes; on the rework path, the **grouping** comes from the routes that exist, and that is all the old app contributes. **Each archetype's shell is proposed fresh, from the new direction** — the shell slot's answer, the brief, and the designer's own judgement of what this kind of screen needs; the shell a page has today is never the template, and it surfaces only as the *old* column of the judgement's shell question. A derivation that reads the existing page to learn "what this archetype's shell is" has imported the old design through the one door left open for routes. Then draw **every page**, each to its archetype's proposed shell — content from the function inventory on the rework path, from the PRD on the fresh path. Pages sharing an archetype will read similar; that is the app being consistent, not the canvas being lazy. This is the full redesign, visible up front — the whole app before a single real file moves.

**`/styleguide` is generated before the canvas**, to `F6`'s spec, rendering the current theme — library defaults on a fresh app. It imports production tokens, so when ratification later writes the new values it follows by itself. Nothing on the canvas depends on it, but the component inventory existing first keeps the canvas honest about what the library actually ships. **In a rework-path overhaul the route already exists and keeps rendering the old theme — leave it alone until ratification, and the canvas never looks at it**; regenerating it first would put the old design on screen in the very session that must draw without it. An older app with no `/styleguide` at all waits the same way: the route is generated inside the pass, from the new tokens, as `R7` orders it.

**Quarantine, both directions.** Nothing in the app imports the canvas, and the canvas imports only from the **declared UI stack** — the chosen component library, the chosen icon pack, the engine libraries the app's dependency file carries for UI jobs (charts, table engines, date pickers, drag-and-drop), and its own CSS. Never the production theme, tokens, or components — the canvas is pre-ratification, and its values are its own until the user ratifies them. The line between the two: a library in `node_modules` is neutral machinery; a production component carries the old design. The app must render identically with the canvas deleted.

**Real components, canvas-owned theme.** The library's components render inside a scoped theme wrapper carrying the canvas's own values — CSS variables on the web. What the user judges is what the app can actually become — no hand-drawn mockups whose fidelity dies in transplant, and no production theme touched while the canvas iterates. **Element selectors in the canvas CSS style native controls only, never the elements inside library components** — a round that swaps native controls for the library's leaves old `input`/`select` rules behind, and they double the library's own borders; scope them out (`:not([data-slot])` or equivalent) the moment the swap happens. **And every control the chosen library ships is drawn with the library's component** — button, input, select, tabs, chip, dialog, pagination, all of them, from the first round, not as a correction the user has to ask for. Hand-rolled markup is legitimate only where the library has no component for the job (a virtualized data table, a bespoke signature element), and each hand-rolled control is named as its own line in the judgement call. A canvas that re-implements the library's buttons has not shown the user what the app can actually become.

**The declared stack binds the engines too.** A job an installed engine owns — a chart, a virtualized table, a date picker — is drawn with that engine, never re-implemented beside it: the promoted page must be the canvas file, so an engine the canvas avoided is an engine the app loses without anyone deciding it. Hand-rolling where an engine covers the job is a departure line at the judgement (`recharts installed → drawn as CSS bars, because Z`), and swapping or dropping an engine is an explicit decision the user answers there — never a side effect of approving pixels; an approved swap becomes its own install/remove line in the pass. Everything the canvas draws with is installed **before** drawing, per the skill's install step. **And before each round is shown, the canvas self-checks itself** — three scans, and a round that fails any of them is not ready to show:

1. **Imports.** Every control maps to a library component or stands as a named hand-rolled line, and every engine import comes from the declared stack.
2. **The render.** Run `impeccable`'s detector over the round's files first — it is deterministic and it owns exactly this scan's subject: clipped and overflowing containers, occluded and overflowing text, broken images, script errors. Fix what it reports here; those are defects, not direction, and deferring a defect to Step 8 ships a broken round to the judgement. **Only the defect class is acted on in a round** — a hit that is a judgement about the direction (nested containers, uniform spacing, a colour family) may be the very thing the user is about to choose, so it travels to Step 8 with the rest. Detector absent, or a rule it cannot see: take the round's screenshots **first and read them yourself**, before the user does. A frame whose content overflows or clips its container, a label naming a size the frame does not actually show, a state drawn as an animation that a still frame renders as nothing — all of it is fixed now. The screenshots are already mandatory (Judging, below), so this scan costs the reading, not the capture. Its licence is narrow on purpose: **clipping, overflow, and labels that lie**. It is not an invitation to re-open composition the moment before showing it.
3. **The arithmetic.** Every number printed as a claim — a ratio, a percentage, a count, a total — is computed, never recalled, and the fixtures close (Coverage, below).

The scan is reported with the round as a short list of what it caught and fixed, not as a claim that it ran. **In `design-settle` the scan covers the fixtures too**: value types and field names come from the existing contract or data-layer modules — an enum, a state label, a column name — and no type name already used there is redefined with different values. Page-structure types are not imported: filter shapes, page sizes, and query keys stay the canvas's to redesign. A field with no source in either is drawn tagged as a proposal, so the user decides it at the judgement rather than meeting it as a dropped element after the pass. An engine need that only emerges while drawing follows `engine-rubric.md`: the frame is drawn with the no-engine rendering and tagged, the judgement settles it, and an approved adoption installs the engine and redraws that frame in the next round.

**The taste license, granted explicitly.** Design the page as a designer with a free hand — no obligation to any earlier conservatism. For a slot answered **"Decide for me"** the license owns everything about it: palette family and its steps, tinted surfaces, elevation, type scale, spacing, composition. For **answered slots** the answers are the user's **preferences — the baseline, not a cage**: the license still covers everything, and **departing is part of the job, not an exception to argue for**. Where the designer judges a better call than an answer, draw the better call, tag it, and ask — one line per departure in the judgement call, shaped `answered X → drawn Y, because Z`. The user settles every departure there: an unapproved departure reverts to the answered value; an approved one enters ratification like any other canvas value. What the tag protects is the user's authorship, never the answer's immunity — a canvas that obeys every answer it privately judged wrong has withheld its one useful opinion.

**And the licence carries a duty: one signature.** Every canvas draws a **single element this app is remembered by** — a treatment, a shell move, a way one recurring thing is rendered — and it is where the boldness is spent. Everything around it stays quiet and disciplined; a canvas where three elements compete to be the signature has none, and a canvas with no signature at all has produced a competent average, which is the outcome this whole path exists to avoid. The signature is **tagged on the canvas like a proposal** and settled by the user at the judgement as its own line, because it is the one decision most likely to be the reason a direction is accepted or rejected. `taste.md` holds what the direction it serves is chosen from.

**Loaded once, in hand throughout — never re-read step by step.** The material arrives before the taste batch and stays for the design plan, every canvas round, the judgement, and the ratification; the only second read in the whole flow is the escalation above. A step that reloads it pays the context twice for the same rules.

**Three pieces of material are loaded before the taste batch, not at drawing time: `references/taste.md` beside this file, and the two Required installs, `impeccable` and `frontend-design`.** The batch's options are the first place taste is exercised, so a batch written before the material is read offers the user a menu of the very defaults the material exists to close — and a choice never offered is not recovered by any later round. By the time the canvas is drawn they have been in hand since the interview. All three are divergence guidance — they name the templated defaults to avoid and the method for choosing a direction, without naming the direction. Material, never an authority: where any of them collides with a user answer or a ratified value, the user wins. One absent, the others still load, and the round says which one was missing; `taste.md` ships with this skill and is never the missing one.

**What crosses the genre line from `impeccable`, and what does not.** It ships far more than material, so the boundary is drawn by file rather than by judgement. **Crosses:** `reference/craft-floor.md` (the Refuse list, and its Verify list as a build-time check rather than an interview input), `reference/new-work.md`'s two calibrations — the sixteen training-data display faces and the three convergence clusters — and `reference/operate.md` entire, which is written for exactly this kind of app: one family often right, a fixed rem scale rather than fluid, a 1.125–1.2 ratio, motion at 150–250ms carrying state and nothing else, overlays that escape their container. **Does not cross:** `reference/shape.md` and the rest of `new-work.md`, which are a complete competing pipeline — its own interview, a dice roll over directions, a decision server, comps, a finish-reviewer subagent, and `DESIGN.md`. Adopting those replaces this flow rather than informing it, and `PRD.md` stays the only document. **Three of its commands are therefore never run in these repos — `init`, `document`, `extract`** — because each writes `PRODUCT.md` or `DESIGN.md`, and those decisions live in PRD Section 5. The `/impeccable` menu leads with `init` whenever it finds no `PRODUCT.md`; that offer is answered by pointing at Section 5, not by taking it. `DESIGN.md` in particular is written by its documenter **from the built world, ground truth over intention** — the `CSS → PRD` direction this skill's hard limits forbid, which is why the file is not adopted rather than merely unused. **The detector reads HTML and CSS, and that decides where it runs.** A web UI qualifies, and so does a desktop or mobile shell whose UI is web technology — Tauri, Electron, Capacitor — because the files it scans are the same. A **truly native** surface does not: SwiftUI, Compose, XAML and their kin compile from source the rule engine has no verdict on, and Impeccable says so itself. Where PRD Section 1's Surface names one of those, every detector instruction in `design-settle` is skipped and reported as `n/a — native surface`, never run and never counted; the checks those steps still owe come from the Surface's own Proof profile. Reporting a zero from a scan that could not read the code is worse than reporting nothing.

**A native Surface loses the detector and gains two references in its place.** `impeccable` ships `reference/ios.md` and `reference/android.md` — safe area and window insets, the platform's own navigation metaphors, Dynamic Type and the Material type scale, and the touch-target floors (44×44pt on iOS, 48×48dp on Android). They are loaded alongside `craft-floor.md` wherever Section 1's Surface names that platform, both of them on an adaptive one, and they carry the rules a web-shaped floor states differently or not at all. Web technology loads neither.

**And two of its playbooks route by platform the way this rule does, so they are named rather than left to be discovered:** `reference/audit.md` (web) and `reference/audit.native.md` cover the technical dimensions Step 8 verifies — accessibility, performance, theming, responsiveness, implementation integrity — with the touch-target floors this repo no longer states anywhere else; `reference/adapt.md` and `reference/adapt.native.md` carry the width and device-class rules. Read the one matching Section 1's Surface when a step needs a floor or a device-class list; the rest of them are command playbooks and stay outside this line.

**And one collision, decided here:** `reference/colorize.md` derives OKLCH ramps by varying lightness and reducing chroma at the extremes. Where a ratified Section 5 line says otherwise, Section 5 wins, as it does over every line in this file.

**What crosses the genre line from `frontend-design`, and what does not.** It is written for the open web, and its body leans toward marketing pages — the hero as a thesis, landing-page anatomy, the question *what makes this unforgettable*. These apps are internal operational tools, judged on the tenth use rather than the first, so read it for what transfers and leave the rest: **the calibration** (the defaults that read as generated), **the two-pass method** (state the plan, critique it against the brief, say what changed), **the signature**, and **the restraint** — spend the boldness once, then remove one thing. What does not transfer is the marketing anatomy, and chasing *unforgettable* with anything that costs speed of use. On an operational tool **the aesthetic risk is the signature and nothing else** — one element, not a posture worn across every screen: a dashboard somebody reads forty times a day pays for a posture every one of those times. `taste.md` applies whole; this boundary is about the other file.

**The line the ban actually draws.** What is never loaded is a skill that names **the look** — a fixed palette, a fixed pairing, a card recipe, a shadow scale to copy — because read for every app, a house style makes every app look like the house. What is loaded, and must be, is guidance that **narrows the space the look is chosen from**: the defaults that read as generated, the formula that keeps two accents in one family, the four typefaces that are a failed choice rather than a safe one. The first names a point; the second removes a region. A canvas given the taste licence and no material at all is not neutral — it falls into the defaults, and *generic* is the name of that failure, not an accident of it.

**The canvas carries its own foundations board, as a page of its own** — palette roles and steps with their values, text scale on real sentences, spacing, radius, shadow, status triads — rendered from the canvas's own variables: a live preview of what `/styleguide` will hold permanently once the values are ratified. **The entry route lands on the primary role's landing page, never the board** — the canvas is judged as the app, and its first impression is a working screen, not documentation. The board hangs in the canvas chrome's nav as its own entry, **set apart from the page groups** so it cannot be mistaken for an app page — one click from every page wearing its values. **And it renders inside the same chrome shell as every other canvas page** — sidebar, top bar and content area where that is the shell those pages wear; only its content is the system rather than the app. A board rendered bare breaks the one navigation pattern the canvas exists to demonstrate.

**How a token is shown: applied to itself, every other variable held constant. Never a table row.** A list of nouns is satisfied by two columns of name and value, and two columns of name and value is the generic output this path exists to prevent. So:

- **Spacing** is a square literally that many pixels, the steps set side by side so the ramp is a staircase. A degenerate value still renders a labelled marker rather than nothing — floor the drawn size.
- **Radius** is identical tiles differing only in corner, so the eye compares corners and nothing else.
- **Shadow** is identical surface tiles that actually cast, with vertical room around them so the shadow falls instead of being clipped by its neighbour.
- **Border width** is identical tiles differing only in stroke.
- **Colour** is a swatch of fixed size carrying the step name, the resolved value, and the semantic alias that points at it — with a hairline inset ring so near-white steps keep an edge. **Grouping is carried by the gap**: tight inside one ramp, looser between families, so the structure is read before anything is labelled.
- **Type** gives every step **a different real sentence from this app's own domain** — the sentence that step actually carries on a screen. One repeated neutral string is allowed on the weight specimen alone, where holding the words constant is the point.
- **The alias layer gets its own row**: role, the step it points at, the resolved value. That layer is the API the components actually use, and a board that shows only numbered steps has documented the palette while hiding the system.

**Every specimen carries a caption in one identical treatment across the whole board** — monospace, muted, small — printing the token key **and** its resolved value together (`lg · 8px`, `hairline · 0.5px`). An absurd literal is relabelled rather than printed (`full`, not `9999px`). The caption is what makes the board usable by an engineer instead of only viewable by the user.

**And the board carries the contrast section** — one row per foreground/background pair the theme defines, the two colours rendered live as a chip of the real foreground on the real background, the computed ratio printed beside it, and its mark against the 4.5 / 3.0 floors. Ratification (below) is where the numbers come from.

**The canvas's variables carry the production token names.** The vars are the canvas's own, but named exactly as the theme files will name them — ratification is then a copy, not a translation, and nothing gets renamed on the way into production.

**Coverage.** The whole visual language, shown once across the pages: every color role in use on real surfaces · text steps on real sentences · one dense table with messy fixtures (long labels, large numbers, missing values) · form controls in their states · **every conditional branch of a form as its own frame — a status that reshapes the fields (deal / no deal) is two frames, never one frame with a note** · status markers · one card or KPI group · **the busy state of every long-running operation — import, matching, bulk delete — as its own frame, carrying real counts** · the loading, empty, and failed state of every page that has one, drawn as frames — promotion adds data, never markup · the behavior at both widths. Realistic domain data from PRD Section 4 — the same standard `build-flow` holds every page to.

**And the numbers must close.** `contract.md` already prefers fixtures **copied** from the document the app replaces, and copied rows close by construction — this rule is for the case that file names as the fallback, where no real document could be used and the figures were invented. Invented figures are plausible one widget at a time and incoherent across a screen, which is exactly what makes a dashboard read as a mockup instead of a report. So on every page:

- A headline total equals the sum of the parts rendered beside it, and a remainder equals the difference it claims to be.
- A percentage, a ring, or a progress bar equals part over total to the precision it displays.
- A top-N list sums to less than its headline, so the tail it implies is plausible.
- A bar width is **computed from the value printed next to it**, normalised against the largest in the set — never a width typed by hand.
- A pagination label's range matches the rows actually rendered, and its last page equals the total divided by the page size, rounded up.
- A sort affordance's claimed direction matches the order of the data underneath it.
- One fictional record named in two places is named identically in both.
- Totals are **derived from the fixture array** rather than typed as literals, so the two cannot drift apart in a later round.

Numbers, dates, thousands separators, and currency follow the app's own locale, as `CLAUDE.md`'s Locale row states it.

**One pattern per recurring control.** Row actions, pagination, summary bars, filter rows: each takes exactly one form across every page — the active page visibly marked, the same action affordance on every table. A second form of the same control is a finding at the judgement, not variety. And **fixture text and labels are written in the user's language** — the canvas is the app being judged, and its strings follow the same language rule as production screens.

## Judging

**The platform is proven, not assumed — and the proof is a list, not an impression.** PRD Section 1 names the platform. On anything other than the web, put the canvas beside one real application native to that platform — a reference the user already named in the taste batch where one of them is native, otherwise one named at this step — and write the differences out one by one: window chrome, navigation shape, control size and radius, icon family, type, accent. Each difference is then either a **departure** with its reason on one line, or a **correction round**. "It looks native" is not an output; the list is, and a list nobody could have written means the comparison was never made.

Why it is a rule rather than taste: every other gate here measures the canvas against this app's own answers, so an app that answers every question in the web's vocabulary passes all of them and still arrives looking like a web page in a window. This is the only step that measures it against something outside itself. On the web that trigger does not fire — there is no OS language to diverge from.

**The same list runs, on any platform including the web, whenever the user named a reference.** An app named under Other is called an anchor the canvas designs toward, and an anchor nothing is measured against is a wish. So put the canvas beside it and write the differences out one by one — density, colour temperature, type character, motion budget, shell shape, how a recurring control is rendered — and settle each one as a **departure** with its reason on one line, or as a **correction round**. *"It feels like the reference"* is not an output; the list is, and a list nobody could have written means the comparison was never made. The reference the user named is what the list is written against, not what the canvas is made to imitate: the bound in "Measured, never transplanted" above still holds, and a difference kept deliberately is a departure like any other, not a failure.

Screenshot at the Section 5 desktop breakpoint (1440px when none exists yet) and at the derived lowest supported width, with the browser tooling available to the session. On a platform whose PRD Section 1 Proof profile names something other than a browser, capture through that profile's Visual line instead — same two bounds, or the platform's equivalent.

**Shown inside its device.** The narrow capture is presented inside a phone frame and the wide one inside a window frame — a bare browser screenshot reads as a web page rather than as a design, and the frame is what tells the user which of the two bounds they are looking at without a caption. **No fake chrome inside the frame**: no painted status bar, no painted keyboard, no fake tab strip carrying content — on a real device the real ones render on top of the layout, and a painted copy reads as doubled. **The frame belongs to the canvas chrome — the entry route — and never to a page file**, so promotion still copies the page element for element and the diff stays confined to the data seam. A session with no capture tooling reports the run target and both widths as it does today; it does not draw a frame around nothing.

The user judges. Two **correction** rounds on the same canvas — rounds opened by the user rejecting what was drawn; a third does not run, the canvas has spent its rounds, and the escalation above opens. A round opened by the user **asking for something new** is not one of those and is not counted; it quotes the request it serves, and a round that cannot quote one is a correction round. Without that split the cap is refused rather than obeyed — a session told to escalate over a request the user just made will write itself an exception instead, and an overridden rule costs context in every session while protecting nothing.

**Escalation decides values, not pixels.** Its answers become the brief's constraints, and the canvas is **regenerated fresh from them** — never patched over the failed one — then judged again under the same two-round rule. **Regeneration replaces the direction, never the decisions:** every feature proposal the user already approved and every shell already ratified carries into the regenerated canvas. A fresh canvas that arrives without an approved feature has silently reopened a settled decision — a page that was full last round and is empty this round is that failure showing.

**Every decision in this path goes through the AskUserQuestion tool**, under the rules `interview.md` states — a prose question at the end of a turn is answered by no one. **Every label in those dialogs is written in the words the user uses, never this file's** — *ratify*, *seam*, *archetype*, *departure* are vocabulary for the session, and a label the user has to decode is a dialog answered blind. Say the action instead: keep this value, use the new layout, delete this page. The judgement is one call: a single-select verdict (approve · rework this round · escalate to the questions), the marked-feature multi-select above, the answer-departure lines for answered slots, and the shell questions — in a rework-path overhaul one per archetype, old shell beside new, **departed or not** (a shell question asked only on departure makes sameness free and departure costly, which is the anchor working); in `design-settle` one per archetype the user's archetype-table correction did not already settle. Four questions per call is the tool's cap — more archetypes means a second call in the same turn. Contrast failures, cancelled value lines, and reopened questions are asked the same way.

**The signature is its own question, asked on its own.** Not a line riding the verdict call among six others — one AskUserQuestion, naming the element, saying what it costs the pages around it, and offering keep · redraw it once · drop it and accept the quieter page. It is the single decision most likely to be the reason a direction is accepted or rejected, and the licence exists precisely to stop the canvas settling into a competent average; a question that arrives as item four of seven is answered by momentum, not by judgement. **A user who cannot recall being asked was not asked**, whatever the transcript shows. A signature the user rejects is redrawn once — never dropped silently, and dropping it is an answer only the user gives.

**Two more lines ride the verdict call whenever they exist**, each settled like a departure: the **reference differences**, where the user named one · the **direction candidate** the user picked, named, so a later round cannot quietly drift off it.

## Ratification — approval happens on the canvas, the values follow as a report

**Approving the canvas is the approval.** The values behind it are then read — the canvas's variables and measured values: palette and its steps, type scale, spacing, radius, shadow, density numbers — and reported the way derived decisions are reported: one line each, never silent, cancellable. Cancelling a line reopens that value as a question; the rest proceed. There is no second approval gate over the same pixels the user just judged.

Two cases still stop:

- **Contrast — computed, never recalled.** Every foreground/background pair the theme defines is run through the WCAG relative-luminance formula and the ratio is **calculated**: a ratio written from memory or judged by eye is the one error a handoff document must never carry, because everything downstream trusts the printed number instead of re-measuring. Compute it where the board renders — the foundations board already carries the contrast section (above) — so the numbers and the chips come from one source and cannot disagree. Every semantic family's dark shade is **chosen by measuring it against its own light shade until it clears 4.5**; that is what the dark shade is for, and picking it one step along the ramp is how a badge ends up unreadable. A failing pair is put to the user, never silently passed and never silently fixed. A passing pair still prints its number.
- **`design-settle`.** Section 5 there already holds decided values, and it changes only by explicit user decision — so the report is not enough: the values enter the gate (its Step 6) as the *new* column of the diff, and that line-by-line approval is the one gate. The canvas judgement and the diff never double up; the diff is where the old value is protected.

Ratified values are written into Section 5 and the styling files under `F6`'s rules, all five — in `design-settle`, only after its gate approves, as the pass's first act on its own branch. The styleguide already exists and follows the new tokens by itself — verify it against `F6`'s done-check, then the pass runs.

**No reference page exists — the canvas is the reference, and approval promotes it.** The canvas pages are structured like the real ones, so the pass **copies each file to its real path** — the most data-dense page of the primary role first — removes the canvas theme wrapper (the token names are already production's), and replaces the fixtures with the real data layer as `build-flow` and `logic-settle` prescribe. **Copied means the canvas file becomes the page** — a production page rebuilt by re-tokening its old markup is not promoted, however redesigned it reads under the new chrome. **And promotion is element-for-element**: every visible element of a canvas frame either survives into the page — fixtures swapped for data, real states added — or appears as a named deviation line at the recap with its reason (real behavior contradicts the drawing · the backend does not exist yet · the control is obsolete). Substituting a plainer equivalent silently — a bare file input where the canvas drew a dropzone — is a failed promotion; and the reverse case, a canvas control the real flow never had, is a canvas error to report for the user's decision, never to quietly drop. **The proof is a diff, not a look**: put the canvas file beside the promoted page — the differences must be confined to the data seam (the fixture import swapped for the data layer, plus its loading and error wiring) and to approved deviation lines; any other difference is a failed promotion to fix, whichever side reads better. **And the foundations move first**: everything the canvas CSS carries beyond token values — the font loading itself, element-level rules, shadows, motion durations — lands in the production styling files before any page moves, and is verified in the browser by computed style: the fonts must resolve to the loaded webfonts, not to a fallback stack. A token grep cannot see a font that never loads. **The shared chrome components a canvas page imports are part of that promotion**: each one lives in the production chrome before any page importing it counts as moved — a shared wizard or card dropped on the way over silently downgrades every page built on it to a repaint. **The ratified original stays behind, frozen** — the lifecycle below says when it dies. On the fresh path there is usually no backend yet: promotion keeps the contract fixtures in `build-flow`'s shape, and real wiring arrives page by page through the queue; on the rework path the existing data layer is wired in the pass itself. What is checked per page, at both widths, is **survival of real data**: a layout that collapses under real rows, a token that did not land, a section that vanished — that is divergence, and the first one stops the pass as a rework round of that page, two at most before Section 5 reopens. Real rows differing from fixtures is not divergence. `/styleguide` embeds no page — the app itself is the composition, one route away. The densest page simply remains the bar `build-flow` judges later pages against.

**A ratified canvas file outlives its promotion as a frozen reference, and dies with its page's real implementation — never before.** The user approved those pixels; until the real page carries real data and survives both widths, the canvas file is the only thing to compare it against. Three rules keep that from becoming drift:

- **Frozen.** A ratified canvas file is never edited again, and never a source of values or patterns — Section 5, the theme files, and the promoted page are the sources; the canvas file is comparison only.
- **Deleted per page, beside the proof — and only with the user's word.** The session that wires a page with real data and sees it survive both widths puts the real page beside its canvas file, fixes what silently diverged, then **proposes** the deletion at a chat stop — naming the page, inviting the side-by-side look, then ending the turn; never through an AskUserQuestion, which would cover the comparison being read — and deletes only on a granted confirmation. Never delete unasked: the canvas file is the only comparison the user has, and a session convinced of its own parity is exactly the session that must not be the judge of it. `build-flow` carries this for pages wired later through the queue; in `design-settle` the pass wires in-session, so one confirmation at its verification step covers the whole canvas.
- **Remnants go last.** The entry route, the foundations board, and the canvas CSS are deleted when the last page file goes — the CSS's values have long lived in the theme files by then.

A canvas file that outlives its **implemented** page is the second source of values the styleguide exists to prevent — that, not the comparison period, is the failure.

## What the canvas never decides

Page content (`build-flow` Section 4) · the archetype table — the canvas proposes every shell on screen, but the table becomes real only through the user's archetype-table correction and the judgement's shell answers · loading, empty, and error norms (`ui-build`) · anything the user does not ratify.
