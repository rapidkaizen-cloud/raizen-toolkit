# Frontend interview — reference, the stack, then the frames

**The interview is small on purpose.** One question alone — the reference, multi-select — then the stack, recommended in the install block rather than asked, then 2–4 direction frames, drawn in every session, that the user picks from on screen. **Nothing about the look is asked after the pick**: the picked frame is the direction, and every value it carries is read at ratification like any other canvas value. Everything else is the designer's call, made on the canvas and reported as a cancellable line — never a dialog, never silent. A long interview does not produce a designed app; it produces a questionnaire's average. The design happens on the canvas (`canvas.md`); the interview exists to capture the preferences the user already has, not to manufacture opinions they do not.

## Where options come from

**Every option, and every frame, is invented for this app, from the model's own design knowledge.** Read the corrected Step 1 reading — the kind of app, the platform, who uses it — and write options the way a designer pitches directions for exactly this product. No fixed option list exists anywhere, and **no research pass runs for taste**: the knowledge that names a good direction for a logistics dashboard or a Windows inventory tool is already in the model, and a search adds latency, not taste. The one place research survives is the stack below, because an install mis-remembered costs far more than a correction round.

Rules per option:

- **Named in plain words, consequence in parentheses.** The user is a junior developer — the parenthetical is what the choice buys or costs, written fresh for this app. No sample phrasing is written in this file, on purpose: a written example gets copied, and a copied option is a stock option.
- **A well-known product is welcome shorthand** when it genuinely fits this app — never name-dropped for its own sake.
- **Off the web, the target platform's design language is always one of the frames**, drawn in it and named as such. On a cross-OS shell (Tauri, Electron, Flutter desktop) the target OS is read from where PRD Section 2's users actually sit, pinned at the Step 1 correction where the PRD does not settle it.
- **A stock option that would fit any app is a failed option.** Every option and every frame must be arguable from this PRD or this platform — if the argument cannot be written in one line, replace it.
- **One option is marked "(Recommended)"** — a real direction with a reason from this app. The reference slot is the one exception, because it is multi-select and its recommendation is a set: the one recommended product **and** "Decide for me" both carry the mark (below). On every other dialog "Decide for me" is never the recommendation.

## The order — reference, the stack, then pictures

**The reference slot is asked alone, before anything else, in its own turn, multi-select.** It does not decide whether the frames are drawn — they are drawn in every session, **2–4 full-fidelity screens of this app, with the real packages**, and what the user picks there *is* the direction. What the slot decides is what each frame is anchored to: every tick becomes a frame, and the frame names its anchor in its own motivation line, so the canvas built from the pick is measured against that anchor at the judgement.

**Then the stack, recommended rather than asked** (below). It comes before the frames because they are drawn with the real packages: the install runs before a single frame exists, so the frame the user picks is already the canvas file and already the production file, with nothing exchanged on the way.

**Then the frames, and nothing after them.** This is the whole reason the order is this way round. A junior developer asked to choose between *Dense data-first* and *Warm editorial* as two lines of prose is being asked to imagine two products and compare them — and the honest answer to that is "Decide for me", which is the answer a slot interview keeps receiving. After the frames there is nothing left to imagine, and nothing left to ask: density, palette, surface, type, motion, and shell are all on the picked frame, and a question re-asking what the user just chose on screen is answered by momentum. What the user wants changed rides the pick under Other — *the second one, but with the brand green* — read as that frame with the correction attached, applied as the frame is finished. What the designer decides beyond the frame surfaces at the design plan and the ratification report as cancellable lines (`canvas.md`).

**Every question goes through the AskUserQuestion tool, single-select — the reference slot alone is multi-select**, because its ticks are added up into a set of frames rather than chosen between. The lead question's text invites everything the options cannot hold: *anything you want that isn't listed — a screen you liked, a hard requirement — type it under Other.*

**"Decide for me" is a real answer, not a failure to answer, and it is never silent**: on the reference slot it fills the frame slots the other ticks leave open, each frame working to an anchor of the designer's choosing, named in the frame's own motivation line, and what the designer chose surfaces in the ratification report like every other canvas value.

**Where UI exists, the reference slot carries `Keep — today's look` first** — where Section 5 is filled the label also names the reference it records — with its consequence in its own text: ticked, the app as it runs today stands among the frames as one candidate, at its real routes, never redrawn. An option, never the recommendation: the user opened a redesign, and recommending today's look back re-litigates that choice. Every other value the redesign derives is reported naming the value the app holds today, and cancelling that line opens a dialog with `Keep — <today's value>` first.

### The reference slot

**The options are real products, proposed by name.** Up to three the model actually knows, each one arguable for *this* app and this platform — never a famous name dropped for its own sake, which the option rules above already forbid. Each option's consequence says what picking it buys in one clause (`the density and the keyboard-first feel of a tracker built for daily use`), not what the product is. One is marked "(Recommended)" and listed first; `Decide for me` carries the mark too, and the question text says why the pair is the recommended answer — one anchor of the user's, the rest of the set the designer's, which is the widest spread four frames can hold. No research pass runs here: naming products a working designer would name is model knowledge, and a search adds latency rather than taste.

Four options is the cap, so the slot carries: up to three named products · **`Decide for me`**. The question is multi-select, and its text says what a tick does, in the user's own words: *every product you tick is drawn as one direction; tick "Decide for me" and I fill the rest of the set with directions of my own, each one saying what it takes after; you pick on screen.* Where UI exists `Keep — today's look` takes the first place, and the named products trim to two. **That option carries its own consequence in its description — ticked, the app as it runs today stands among the frames, at its real routes, never redrawn**, so what is kept is judged beside what could replace it; ticked alone, without `Decide for me`, the second frame is one reading of today's look redrawn on a named axis, like any lone tick below, so the set is never one frame. The user's own answer arrives through Other — a product the options missed, a screenshot, a file, a URL — and that is the best outcome, not a deviation: an Other product is one more anchor, one more frame. Other carries text only, so the question text says how a picture arrives: *answer "screenshot" under Other and paste the image in chat* — and the session reads it, and takes its numbers off it, before the first frame is drawn (`canvas.md`, Measured, never transplanted).

**The ticks add up to the set of frames, by four rules.** Each ticked product — a Keep, an Other product included — is one frame anchored to it. `Decide for me` fills the slots the ticks leave open, up to the cap of four, each frame to an anchor of the designer's choosing — **a product, or a thing from the world this app's subject lives in**: an object, a place, a medium its users already picture when they think of that subject. A set anchored to products alone inherits the look of the nearest software, and for a tool the nearest software is grey. Each anchor is of a different kind than the products the user ticked and than each other — a user who ticked a tracker is not handed a second tracker as the designer's idea; off the web the platform's own design language holds one slot before it fills any, and where no slot is left it adds nothing and the design plan says so. A lone tick — one product, or Keep alone — without `Decide for me` still yields two frames: the second is a second reading of the same anchor on a named axis (dense against airy, warm against cool), never an anchor of the designer's own, because the user did not ask for one. And every frame, whoever chose its anchor, **names that anchor in its own motivation line** — the difference list at the judgement runs against the anchor of the frame the user picked, like a reference they had chosen themselves. What is never allowed is an anchor that goes unnamed: an anchor nothing is measured against is a wish, and one the user never saw is a wish they cannot cancel.

**Nothing stands the frames down** — not a ticked product, not a brand palette, not Keep (`canvas.md`). A product is one frame's anchor; a brand palette is a constraint every frame is drawn under, colour derived from it (`canvas.md`); Keep is a frame. A user who names a product knows the direction in words, and words are what the frames are cheap insurance against: a wrong reading of a named reference costs a correction round that redraws the whole app, where a second frame costs one screen. A user who ticks only "Decide for me" is telling you they cannot answer in words — the frames are the answer to exactly that, not a licence to skip asking.

**What an anchor actually costs and buys** is stated in the question text, because it is what changes at the judgement: the canvas is put beside the anchor of the picked frame and every difference is written out one by one, each settled as a departure with its reason or as a correction round (`canvas.md`, Judging). This holds whoever chose the anchor — a product the user ticked, or an anchor the designer named under `Decide for me`, product or not.

**A reference sets direction, never reproduction.** It is measured where reachable and never transplanted (`canvas.md`); imitating a company's distinctive interface is refused however the request is phrased, and an option that would amount to that is not offered.

**Four options is the tool's cap, and four frames is the set's.** Where the slot also carries a Keep entry, the named products trim to fit — the cap trims products, never the Keep or the "Decide for me" entries. Three products plus `Decide for me` is four frames; Keep plus two products plus `Decide for me` is four frames.

**A correction that collides with the pick goes back as one question.** A brand hex attached under Other that fails contrast on the picked frame's ground, a reference named beside a frame that departs from it — name both and what collides, offer keeping either side and a named middle path where one exists, with a recommendation. The resolved answer replaces the original before anything downstream reads it.

## The stack — recommended in the install block, because it installs code

Taste can be improvised and corrected; an install cannot — and the frames are drawn with the real packages, so the stack is settled before them. It is **recommended, not asked**: the skill's install block carries one line per decision with its recommendation, its reason in a clause, and its alternatives, and the block's approval in chat is the answer — a reply naming an alternative rewrites that line and shows the block again. No dialog opens for it: a gate that stands before the user has seen a single picture should cost one read, not four questions.

- **Component library** — candidates scored and verified under `library-rubric.md`; the line names the recommended library with what it bundles and what it leaves out, and *own components* is always among its alternatives, each alternative in a clause. Where UI exists the recommendation is *keep* unless the audit indicts the library itself.
- **Styling approach** — **derived from the library line, never a line of its own.** A library that ships a styling system decides this: shadcn requires Tailwind, MUI brings emotion, Mantine its own CSS layer. Report it with the value and the library it came from, cancellable like every derived decision. It becomes a line of its own **only** where the library implies nothing — own components, or a platform with no library at all — and then its candidates are assembled under `library-rubric.md`'s method like any other package, never named from memory. `app-settle` deliberately writes no styling default at bootstrap, because the library decision arrives here.
- **Icon pack** — a line only when the chosen library bundles none; the recommendation is the pack already installed alongside it when there is one. **One icon family per app, no exceptions** — an icon missing from the family is a finding, never a hand-drawn SVG or a second family.
- **Engines** — charts, heavy tables, date pickers, drag-and-drop and the rest: no standing line. Dialogs fire only on `engine-rubric.md`'s triggers, before the block, and an app that trips none hears none; what they decide enters the block as lines.

**The verification duty for stack candidates stays** — maintained, adopted, what it bundles versus what it leaves out, per `library-rubric.md` and `engine-rubric.md`. One verification pass covers all candidates together; never one search per option, and never a candidate offered on memory alone.

**The family rule.** PRD Section 1 records the logic-layer choices with their families (`TanStack Query — TanStack ecosystem`). Whenever a candidate list includes a member of an already-installed family, that member rises to the recommendation, provided it passes the rubric's own checks — and the shift is named when recommending ("recommended also because Query is already installed"). A shift moves the recommendation, never removes an option.

## What the designer settles — reported, cancellable, never silent

Everything a long-form interview would have asked is the designer's call on the canvas, surfaced through the reports that already exist: the design plan after the pick, the assumptions block before drawing, and the ratification value report after approval (`canvas.md`). One line each, and the user may cancel any line — cancelling opens that value as a normal dialog with real options. What this list saves in questions it must not lose in visibility.

What it covers, with the floors that are rules rather than preferences:

- **The values the picked frame carries** — palette and accent, surface, density, typography, motion, shell — read off the canvas at ratification, never re-asked. **Motion honors `prefers-reduced-motion` whatever was drawn** — that part is a rule, not a value.
- **Theme mode** — light, dark, both, or following the system. A product call, not a taste value: derived before the frames from PRD Section 2 — who uses the app, when, and where (a night shift or a control room argues for dark; a form filled at a desk, for light; a public page, for following the system) — named in the line that hands the frames over, repeated in the canvas assumptions block, cancellable at either. The frames and the canvas are drawn in the derived default — one frame of the set may depart from it (`canvas.md`, Directions first), and picking that frame settles the mode; where two modes are derived, the second is proven on the foundations board and `/styleguide` at ratification, every contrast pair computed in both, and Section 5 records the modes supported.
- **Contrast** — WCAG AA (4.5:1 text, 3:1 non-text) is the floor, from `impeccable`'s craft floor Verify list, which `ui-build` loads before any component is written; off-web the platform's own accessibility bar applies where it is stricter (its iOS and Android references).
- **Status colors and markers** — how many statuses, their hues and tints. **Color is never the only marker**: an icon, label, or shape rides with it, readable by someone who cannot tell red from green.
- **Text scale, spacing scale, hover steps** — the designer's own, read off the canvas at ratification.
- **Supported and judged widths** — the lowest supported width derives from PRD Section 2's roles: a field or phone role pulls it down to phone width, an all-desk cast keeps it at desktop; the desktop judged width becomes the Section 5 desktop breakpoint. Off the web, both are read from and kept consistent with the Proof profile's Bounds line. Both widths are named in the canvas assumptions block — the round-1 screenshots are taken at them — and the lower bound is stated explicitly in Section 5, so anything below it is *unsupported rather than broken*; without that sentence, every "looks wrong on my phone" report becomes work nobody decided to take on.
- **Tables, feedback placement, confirmation guards, form layout and validation timing** — the designer follows this app's platform conventions and the chosen direction, not a fixed web idiom: a desktop application follows its OS's own idioms; the web follows the chosen references. Two guards stand whatever is drawn: an irreversible action gets a confirmation, and permanent mass-deletion gets a stronger one; **a placeholder never replaces a label**.
- **Copy on controls and labels** — wording, label length, and supporting text are the designer's, judged on the canvas in the app's on-screen language (the Locale row of `CLAUDE.md`); where UI exists the audit's measured label and supporting-text counts are the evidence they are judged against. What stays fixed is accessibility, not taste: an icon-only control carries its verb in `aria-label` and a tooltip, and a destructive confirmation and a page's primary action are never icon-only.

## The archetype table

Derived once the frame is picked, never asked page by page. Group every page of PRD Sections 2 and 3 into **screen archetypes** — usually 4–7 (auth, dashboard, data table, form, wizard, detail/approval recur on an app; hero, benefit section, pricing, social proof, and CTA/footer recur on a landing page, where the unit an archetype groups is the section rather than the route). Per archetype one row: shell layout in one sentence, the components it is built from, its density, its empty/loading wording, and the routes it owns. Every route lands in exactly one archetype; a page fitting none is put to the user as its own question, never silently given a bespoke layout. The table is shown once for correction — as a report, not a dialog per row. The ratified table is written into Section 5 under Page Composition, and `build-flow` Section 4 opens every later page proposal by naming its archetype.

## Non-web platforms

The options and the frames are product-shaped, so off the web the vocabulary substitutes before any of them is written: the **design language** — one frame is drawn in the target OS's own and named as such; the **unit** — the platform's own rather than the CSS pixel, so widths read as window minimum size or size classes in dp; the **shell** — one frame carries the platform's own navigation model rather than sidebar-or-top-bar. The canvas's native side-by-side proof (`canvas.md`) is what holds the result to the platform — the interview only has to keep the vocabulary from silently defaulting to the web's.

# What is not asked

Loading, empty state, and error placement are **not decisions here**. All three are fixed norms in the `ui-build` skill of `raizen-norms`, identical across every app under these skills.

Wording is fixed there too, in that skill’s `Writing` section — voice and tone, button and link text, capitalization, toggle labels, error phrasing. None of it varies per app, so asking spends context on an answer that is already known. **How long a label or a supporting sentence may run is capped nowhere**: it stays the designer’s, judged on the canvas, and `build-flow` prints each page’s longest and median so drift is visible without a ceiling to write up to.
