# The design canvas — taste decided on a free page, not by questions

One temporary TSX route — **every page of the app, redesigned** — where the visual direction and every shell are designed whole, judged in the real browser, then ratified value by value into Section 5. It replaces the **taste** questions of the interview; it never replaces the structural ones.

## When this path runs

- `design-init`, in **Full mode** (the interview runs first, the canvas renders its answers — the default recommendation) and in **Fast mode** (the canvas improvises the values too).
- `design-rework` overhaul, same two routes — full or fast, the user's pick at Step 2.

**Escalation when the canvas misses twice:** on Fast, the full interview opens; on Full, decisions 1–3 are re-asked. The structured questions dig out what the free hand could not.

## The brief — features in, interpretation free

The input to the canvas is the **user's feature list**, plus what the PRD already holds. The user names what the app does; the canvas decides how that looks — composition, richness, hierarchy are the designer's to interpret, and the user judges the result rather than pre-approving a layout.

Two bounds on that freedom, both the user's own condition:

- **Function is faithful.** A feature on the canvas shows what the feature actually does — its real fields, its real states, the figures a business rule demands. What stays forbidden is the **untagged** invention: an improvised feature drawn without its proposal tag, or promoted without ratification. Tagged improvisation is not the exception this rule guards against — it is the canvas's job, granted below.
- **It renders working — static data, live chrome.** Real fixtures, not lorem; states, not placeholders. The **data** is static by design: nothing fetches, nothing writes, no auth, no validation, no business logic — real behavior arrives when pages are built through `build-flow`, whose Bound list is where *matches the function* is enforced page by page. The **chrome** is alive: sidebar and menu items navigate between canvas pages (plain anchors to the sibling files — no router import, the quarantine holds), tabs switch, a row opens its panel, dialogs and drawers open and close, the collapse collapses — local state over fixtures, nothing more. **An action whose real outcome is navigation navigates too:** the login button lands on the home canvas with nothing checked and any input accepted, a work-queue line lands on the page it points at — the walk from login to the deepest page works end to end, and no auth, no session, and no validation is simulated to make it so. The user judges flow as well as composition, and a canvas that cannot be walked is judged as posters; every interaction written here is real component code that survives promotion. A conditional branch that interaction cannot reach cheaply still gets its own frame, as Coverage requires.

**Assume the product whole — expansion is a duty, not a permission.** Before drawing, draft the full product this brief implies: from PRD Sections 1–4, the research pass of `interview.md`, and the designer's own knowledge of the domain — what a mature version of this app would hold, page by page. The product-type database `build-flow` Section 4 draws from is the floor of that draft, never its ceiling. The user naming two features is an opening, not the ceiling — **a canvas that renders a thin brief as thin pages has failed exactly as the safe-default canvas fails.** Draw the full draft, and **mark every improvised feature visibly as a proposal** on the canvas (a small tag on its section). The cut is then **asked, not narrated**: in the same AskUserQuestion call as the judgement verdict, the marked features form a multi-select — every feature an option with a one-line description, keeping all as the recommendation; four options is the tool's cap per question, so more features means more questions in the same call. What is unchecked is removed. Same bias `build-flow` applies per page — propose the full thing, let the user trim — but here the proposal arrives rendered, because a feature is easier to judge on screen than as a line in a list.

A kept proposal the PRD does not yet hold is reported as a PRD line for the user's decision, per `prd-format`: the canvas may show it, only the PRD makes it real.

**In `design-rework` the floor of the brief is the app's function inventory, never its pages.** The audit reduces the existing pages to a written inventory — every function the app carries, one line each, page-agnostic — and that list joins the brief as given. What a page currently *holds* is not in the inventory: "session identity as a card on home" is an allocation the old design made, and the new direction re-allocates freely — a function may move to another page, into the chrome, merge with a neighbour, or shrink to a line. A function the new shell's chrome already carries is not drawn again as page content out of loyalty to where it used to live. Only a function absent from **every** canvas page is a cut, and a cut is asked at the judgement, never silent. Improvised features and reshaped shells are still expected and still tagged — a canvas that redraws today's pages in new tokens is a repaint, and it has failed exactly as the safe-default canvas fails. *Function-faithful* binds what a shown feature does; it never binds a layout to what the layout used to be, nor a function to the page that used to hold it.

**In a full overhaul, the current design is not an input — and Section 5's prose is the current design.** What the app *does* joins the brief as given; how it *looks* today does not — the canvas is drawn as if the app had no visual past, from the answers and the license below alone. That blindness covers the document, not only the code: the old Section 5's visual-direction prose, its signature, its ornament rules, and its archetype shell column are today's design written down, and the canvas may not read them as constraints. A signature worth keeping is re-drawn because the new direction earns it — tagged like any improvisation — never because a ratified sentence demands it. The audit's numbers exist to price the pass and to power the before/after at the judgement, never to anchor the new direction. **And the blindness is enforced by distance, not willpower:** the old page files are opened once, at the audit, to write the function inventory — the drawing phase works from that inventory and the answers, and does not reopen them; the Step 1 screenshots serve the judgement's before/after and the Step 9 comparison, and are not looked at while drawing. A rule that says "don't treat it as input" while the input sits freshly read in context is a rule that loses.

A reference the user points at — a file, a screenshot, an app — is welcome as inspiration for the interpretation. It is **looked at, never parsed or imported**: its values are re-created by the designer where they fit, not transplanted as machinery.

## Asked before drawing

**Fast:** three dialogs only — decision 7 component library · its icon dialog (only when the library bundles none) · decision 10's minimum-width facet, asked directly. **Full:** the whole interview in `interview.md` — every decision's primary axis — and its answers set the canvas's baseline. In `design-rework` every asked dialog carries a `Keep — <today's value>` option, written first but never the recommendation — decision 7 alone recommends keeping the installed library, unless the audit indicts it.

**The research pass of `interview.md` runs in every mode.** In Full it already ran before the first question; in Fast no interview runs, so the pass runs here instead — before drawing, feeding the product draft and the reference apps the improvised values lean on. A canvas drawn without it improvises from memory alone, which is the difference the pass exists to close.

Install per the skill's own install step **before** the canvas is written. The canvas is built from the real packages, so they must exist.

**Assumptions are declared before drawing, in one block — mandatory, never skipped.** Every product and behavior call the canvas makes that no answer settles — layout calls, invented sections, data assumptions, conditional behaviors — is listed one line each (`GPS tolerance shown as a badge with live distance` · `bottom bar: 3 slots, input as the primary action`) before the first file is written. **Visual values are not assumption lines** — palette, type, spacing, radius live on the canvas and are read at ratification; listing them here would report the same decision twice. The block follows the derived-decision pattern: a report the user may cancel line by line, not a gate that waits. The same lines return at the judgement call, attached to what they produced, where the user settles them through AskUserQuestion like every other canvas decision.

## The canvas file

**One folder, one file per page.** `src/design-canvas/` beside the styleguide route: one TSX file per page, **named exactly as its real page is or will be named**, plus an entry route that lands on the primary role's landing page (the chrome's nav is the page list) and one CSS file carrying the canvas variables. Reachable dev-only like `/styleguide`, out of navigation and out of the production build. Never one monolithic file, and never files scattered outside the folder — the folder is the quarantine boundary, and its structure mirrors the app's real pages **so that approval is a promotion, not a rebuild**.

**Every page, drawn.** Derive the archetype table before drawing — group the PRD's pages as decision 10 describes; in `design-rework`, the **grouping** comes from the routes that exist, and that is all the old app contributes. **Each archetype's shell is proposed fresh, from the new direction** — the decision 10 answer, the brief, and the designer's own judgement of what this kind of screen needs; the shell a page has today is never the template, and it surfaces only as the *old* column of the judgement's shell question. A derivation that reads the existing page to learn "what this archetype's shell is" has imported the old design through the one door left open for routes. Then draw **every page**, each to its archetype's proposed shell — content from the function inventory in `design-rework`, from the PRD in `design-init`. Pages sharing an archetype will read similar; that is the app being consistent, not the canvas being lazy. This is the full redesign, visible up front — the whole app before a single real file moves.

**`/styleguide` is generated before the canvas**, to `design-init` Step 6's spec, rendering the current theme — library defaults on a fresh app. It imports production tokens, so when ratification later writes the new values it follows by itself. Nothing on the canvas depends on it, but the component inventory existing first keeps the canvas honest about what the library actually ships. **In a `design-rework` overhaul the route already exists and keeps rendering the old theme — leave it alone until ratification, and the canvas never looks at it**; regenerating it first would put the old design on screen in the very session that must draw without it. An older app with no `/styleguide` at all waits the same way: the route is generated after ratification, from the new tokens, as `design-rework` Step 6 orders it.

**Quarantine, both directions.** Nothing in the app imports the canvas, and the canvas imports only three things: the chosen component library, the chosen icon pack, and its own CSS. Never the production theme, tokens, or components — the canvas is pre-ratification, and its values are its own until the user ratifies them. The app must render identically with the canvas deleted.

**Real components, canvas-owned theme.** The library's components render inside a scoped theme wrapper carrying the canvas's own CSS variables. What the user judges is what the app can actually become — no hand-drawn mockups whose fidelity dies in transplant, and no production theme touched while the canvas iterates. **Element selectors in the canvas CSS style native controls only, never the elements inside library components** — a round that swaps native controls for the library's leaves old `input`/`select` rules behind, and they double the library's own borders; scope them out (`:not([data-slot])` or equivalent) the moment the swap happens. **And every control the chosen library ships is drawn with the library's component** — button, input, select, tabs, chip, dialog, pagination, all of them, from the first round, not as a correction the user has to ask for. Hand-rolled markup is legitimate only where the library has no component for the job (a virtualized data table, a bespoke signature element), and each hand-rolled control is named as its own line in the judgement call. A canvas that re-implements the library's buttons has not shown the user what the app can actually become.

**The taste license, granted explicitly.** Design the page as a designer with a free hand — no database query, no obligation to any earlier conservatism. In **Fast** the license covers everything: palette family and its steps, tinted surfaces, elevation, type scale, spacing, composition. In **Full** the interview's answers are the user's **preferences — the baseline, not a cage**: the license still covers everything, and **departing is part of the job, not an exception to argue for**. Where the designer judges a better call than an answer, draw the better call, tag it, and ask — one line per departure in the judgement call, shaped `answered X → drawn Y, because Z`. The user settles every departure there: an unapproved departure reverts to the answered value; an approved one enters ratification like any other canvas value. What the tag protects is the user's authorship, never the answer's immunity — a canvas that obeys every answer it privately judged wrong has withheld its one useful opinion. The canvas exists because taste assembled from safe defaults produces a wireframe; a canvas that reaches for the safe default has failed its one job. The entries of `anti-pattern.md` still bind, **with their qualifiers** — a purple-blue gradient *as the default*, a *pure black* shadow — guardrails against clichés, never a taste to follow.

**Drawn with the taste material loaded.** Before designing, read `high-end-visual-design` and `frontend-design` as material — their standards and prohibitions raise the floor of the free hand the same way `anti-pattern.md` does. Material, not a live authority: where either collides with a user answer or a ratified value, the user wins.

**The canvas carries its own foundations board, as a page of its own** — palette roles and steps with their values, text scale on real sentences, spacing, radius, shadow, status triads — rendered from the canvas's own variables: a live preview of what `/styleguide` will hold permanently once the values are ratified. **The entry route lands on the primary role's landing page, never the board** — the canvas is judged as the app, and its first impression is a working screen, not documentation. The board hangs in the canvas chrome's nav as its own entry, **set apart from the page groups** so it cannot be mistaken for an app page — one click from every page wearing its values. **And it renders inside the same chrome shell as every other canvas page** — sidebar, top bar, content area; only its content is the system rather than the app. A board rendered bare breaks the one navigation pattern the canvas exists to demonstrate.

**The canvas's variables carry the production token names.** The vars are the canvas's own, but named exactly as the theme files will name them — ratification is then a copy, not a translation, and nothing gets renamed on the way into production.

**Coverage.** The whole visual language, shown once across the pages: every color role in use on real surfaces · text steps on real sentences · one dense table with messy fixtures (long labels, large numbers, missing values) · form controls in their states · **every conditional branch of a form as its own frame — a status that reshapes the fields (deal / no deal) is two frames, never one frame with a note** · status markers · one card or KPI group · **the busy state of every long-running operation — import, matching, bulk delete — as its own frame: a progress bar with real counts, never only a spinner** · the behavior at both widths. Realistic domain data from PRD Section 4 — the same standard `build-flow` holds every page to.

**One pattern per recurring control.** Row actions, pagination, summary bars, filter rows: each takes exactly one form across every page — the active page visibly marked, the same action affordance on every table. A second form of the same control is a finding at the judgement, not variety. And **fixture text and labels are written in the user's language** — the canvas is the app being judged, and its strings follow the same language rule as production screens.

## Judging

Screenshot at the Section 5 desktop breakpoint (1440px when none exists yet) and at decision 10's minimum-width lower bound, with the browser tooling available to the session. The user judges. Two rounds on the same canvas; a third round does not run — the canvas has spent its rounds, and the escalation above opens.

**Escalation decides values, not pixels.** Its answers become the brief's constraints, and the canvas is **regenerated fresh from them** — never patched over the failed one — then judged again under the same two-round rule. **Regeneration replaces the direction, never the decisions:** every feature proposal the user already approved and every shell already ratified carries into the regenerated canvas. A fresh canvas that arrives without an approved feature has silently reopened a settled decision — a page that was full last round and is empty this round is that failure showing.

**Every decision in this path goes through the AskUserQuestion tool**, under the rules `interview.md` states — a prose question at the end of a turn is answered by no one. The judgement is one call: a single-select verdict (approve · rework this round · escalate to the questions), the marked-feature multi-select above, the answer-departure lines (Full mode), and the shell questions — in a `design-rework` overhaul one per archetype, old shell beside new, **departed or not** (a shell question asked only on departure makes sameness free and departure costly, which is the anchor working); in `design-init` one per archetype the user's decision 10 correction did not already settle. Four questions per call is the tool's cap — more archetypes means a second call in the same turn. Contrast failures, cancelled value lines, and reopened questions are asked the same way.

## Ratification — approval happens on the canvas, the values follow as a report

**Approving the canvas is the approval.** The values behind it are then read — the canvas's variables and measured values: palette and its steps, type scale, spacing, radius, shadow, density numbers — and reported the way derived decisions are reported: one line each, never silent, cancellable. Cancelling a line reopens that value as a question; the rest proceed. There is no second approval gate over the same pixels the user just judged.

Two cases still stop:

- **Contrast.** Every new pair is checked against the Section 5 target; a failing pair is put to the user, never silently passed and never silently fixed.
- **`design-rework`.** Section 5 there already holds decided values, and it changes only by explicit user decision — so the report is not enough: the values enter Step 4 as the *new* column of the diff, and that line-by-line approval is the one gate. The canvas judgement and the diff never double up; the diff is where the old value is protected.

Ratified values are written into Section 5 and the styling files under `design-init` Step 4's rules, all four. The styleguide already exists and follows the new tokens by itself — verify it against `design-init` Step 6's done-check, then the pass runs.

**No reference page exists — the canvas is the reference, and approval promotes it.** The canvas pages are structured like the real ones, so the pass **copies each file to its real path** — the most data-dense page of the primary role first — removes the canvas theme wrapper (the token names are already production's), and replaces the fixtures with the real data layer as `build-flow` and `logic-init` prescribe. **Copied means the canvas file becomes the page** — a production page rebuilt by re-tokening its old markup is not promoted, however redesigned it reads under the new chrome. **And promotion is element-for-element**: every visible element of a canvas frame either survives into the page — fixtures swapped for data, real states added — or appears as a named deviation line at the recap with its reason (real behavior contradicts the drawing · the backend does not exist yet · the control is obsolete). Substituting a plainer equivalent silently — a bare file input where the canvas drew a dropzone — is a failed promotion; and the reverse case, a canvas control the real flow never had, is a canvas error to report for the user's decision, never to quietly drop. **The shared chrome components a canvas page imports are part of that promotion**: each one lives in the production chrome before any page importing it counts as moved — a shared wizard or card dropped on the way over silently downgrades every page built on it to a repaint. **The ratified original stays behind, frozen** — the lifecycle below says when it dies. In `design-init` there is usually no backend yet: promotion keeps the contract fixtures in `build-flow`'s shape, and real wiring arrives page by page through the queue; in `design-rework` the existing data layer is wired in the pass itself. What is checked per page, at both widths, is **survival of real data**: a layout that collapses under real rows, a token that did not land, a section that vanished — that is divergence, and the first one stops the pass as a rework round of that page, two at most before Section 5 reopens. Real rows differing from fixtures is not divergence. `/styleguide` embeds no page — the app itself is the composition, one route away. The densest page simply remains the bar `build-flow` judges later pages against.

**A ratified canvas file outlives its promotion as a frozen reference, and dies with its page's real implementation — never before.** The user approved those pixels; until the real page carries real data and survives both widths, the canvas file is the only thing to compare it against. Three rules keep that from becoming drift:

- **Frozen.** A ratified canvas file is never edited again, and never a source of values or patterns — Section 5, the theme files, and the promoted page are the sources; the canvas file is comparison only.
- **Deleted per page, beside the proof — and only with the user's word.** The session that wires a page with real data and sees it survive both widths puts the real page beside its canvas file, fixes what silently diverged, then **proposes** the deletion through AskUserQuestion — naming the page and inviting the side-by-side look — and deletes only on a granted confirmation. Never delete unasked: the canvas file is the only comparison the user has, and a session convinced of its own parity is exactly the session that must not be the judge of it. `build-flow` carries this for pages wired later through the queue; in `design-rework` the pass wires in-session, so one confirmation at Step 9 covers the whole canvas.
- **Remnants go last.** The entry route, the foundations board, and the canvas CSS are deleted when the last page file goes — the CSS's values have long lived in the theme files by then.

A canvas file that outlives its **implemented** page is the second source of values the styleguide exists to prevent — that, not the comparison period, is the failure.

## What the canvas never decides

Page content (`build-flow` Section 4) · the archetype table — the canvas proposes every shell on screen, but the table becomes real only through the user's answers in the judgement call · loading, empty, and error norms (`ui-build`) · anything the user does not ratify.
